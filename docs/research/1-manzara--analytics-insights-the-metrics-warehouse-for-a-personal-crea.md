## Özet

As of Aug 2026 the picture is: platform APIs are the hard part, the warehouse is the easy part. Meta has collapsed Instagram/Threads metrics into a single `views` metric (impressions removed in v22/v23) and keeps only 90 days of IG account insights and 2 years of Page insights, so you MUST snapshot daily into your own store or the data is gone. LinkedIn finally shipped `memberCreatorPostAnalytics` for personal profiles (11 metrics incl. POST_SAVE, LINK_CLICKS, FOLLOWER_GAINED_FROM_CONTENT) but it is gated behind the `r_member_postAnalytics` permission and Community Management API partner approval — the single biggest blocker for a solo operator. X killed its free tier and moved new developers to credit-based pay-per-use. TikTok's Display API gives you your own videos at 600 req/min but engagement counts are inconsistent, and the Research API is explicitly closed to commercial users. YouTube is the most generous: 10,000 quota units/day on Data API, 1 unit per Analytics query, deep historical data. For the warehouse, DuckDB + the MIT-licensed MotherDuck MCP server is the correct answer for a single operator with thousands of rows: an LLM agent gets real SQL over a single file, zero server. Pull data in with dlt (Apache 2.0, declarative REST-API source). For self-hosted product analytics, Umami (MIT, full API self-hosted) and PostHog (generous 1M-event free cloud tier + free MCP server + HogQL) win; avoid Plausible CE, whose Stats API is a paid-cloud feature. For BI, Evidence.dev (MIT, static site, native DuckDB) or Metabase OSS (AGPL). Dub.co removed its free tier ($90/mo floor) — self-host Dub, Shlink or YOURLS instead.

<details><summary>Notlar</summary>

**Instagram Platform Insights API (media + account)** — CRITICAL: account/user insights data is retained only 90 days — you must snapshot daily. Some metrics unavailable on accounts <100 followers. Only one account per request. `impressions` was deprecated (v22, Apr 2025) and removed in v23 — requests for media created on/after 2 Jul 2024 error out; use `views` instead. Reel plays also folded into `views`. Rate limit is Business Use Case: calls/24h = 4800 × impressions (X-Business-Use-Case-Usage header). Meta versions quarterly with ~2yr sunset, so pin a version and diarise migrations.

**Facebook Page Insights API** — Only last 2 years of insights retained, and only 90 days can be queried in one since/until window — paginate. Page must have 100+ likes for insights. Metrics update ~every 24h. BUC rate limit = 4800 × engaged users per 24h with a Page/System User token; 200 × users per hour with an app/user token.

**LinkedIn Member Post Analytics (memberCreatorPostAnalytics)** — 11 metrics as of li-lms-2026-04+: IMPRESSION, MEMBERS_REACHED, RESHARE, REACTION, COMMENT, POST_SAVE, POST_SEND, LINK_CLICKS, PREMIUM_CTA_CLICKS, FOLLOWER_GAINED_FROM_CONTENT, PROFILE_VIEW_FROM_CONTENT. DAILY aggregation NOT supported for MEMBERS_REACHED, LINK_CLICKS, FOLLOWER_GAINED_FROM_CONTENT, PROFILE_VIEW_FROM_CONTENT. Daily IMPRESSION not supported when entity is a post. Docs warn RESHARE/REACTION/COMMENT are 'not consistent with UI'. LinkedIn sunsets API versions aggressively (202507 already sunset).

**LinkedIn Organization Share Statistics (organizationalEntityShareStatistics)** — Historically the only post-level analytics LinkedIn exposed. Easier to get approved for than member analytics if you run a company page for your SaaS. Use this as the fallback if r_member_postAnalytics is denied.

**YouTube Analytics API (reports.query)** — Cheapest real analytics API in this list. Demographic/geo/traffic-source rows are suppressed below undisclosed thresholds. Deleted videos are excluded from per-item reports but included in aggregates. Groups can hold up to 500 videos. YouTube dev policy requires refreshing Data API metadata every 30 days. Multi-dimension queries are still 1 unit but response size grows.

**YouTube Data API v3** — list ops ≈1 unit, search ≈1 unit (but hard-capped at 100/day), writes ≈50 units, upload 1 unit. The 100 search.list/day cap is the real constraint for trend mining — cache aggressively. Quota increase requires an audit form.

**TikTok Display API v2** — Rate limit 600 req/min per endpoint on a 1-minute sliding window; HTTP 429 + rate_limit_exceeded on breach. Documented base fields: id, title, video_description, duration, cover_image_url, embed_link, share_url. Engagement counts (view_count, like_count, comment_count, share_count) require additional scopes (user.info.stats / video.list extended fields) and are inconsistently populated — verify empirically before building on them. Cover image URLs expire; re-query.

**TikTok Research API** — BLOCKER: TikTok's own FAQ states creators, advertisers and commercial users are not eligible. Restricted to verified academic and public-interest institutions, and eligibility has tightened further in 2026. Non-EU/US applicants face extra friction. Do not plan around this.

**X (Twitter) API v2** — organic_metrics and non_public_metrics (impressions, url_link_clicks, user_profile_clicks) are only available for your own authenticated user's tweets and only within a 30-day window. The $0.20 surcharge on link posts is a direct tax on a content-marketing workflow. Cost is now unbounded-ish per call — put a hard budget cap in your pipeline.

**Threads API Insights** — Media metrics: views, likes, replies, reposts, quotes, shares. User metrics: views (time series), likes, replies, reposts, quotes, clicks, followers_count, follower_demographics (needs 100+ followers). HARD LIMIT: since/until do not work before 2024-04-13 (ts 1712991600) and data before 2024-06-01 is unreliable. Publishing caps per rolling 24h: 250 posts, 1000 replies, 100 deletes, 500 location searches; keyword search capped 500 queries per rolling 7 days. Check GET /{threads-user-id}/threads_publishing_limit for live quota. Empty array returned for REPOST_FACADE posts.

**Pinterest API v5 (analytics + trends)** — Trial access is brutally limited: 1,000 requests/day total across everything. Standard access: org_analytics 60/min, org_read 1,000/min, org_write 100/min, trends_read 60/min, ads_analytics 300/min, plus a universal 100 req/sec per user per app. The trends_read endpoint is a genuinely useful free keyword-trend source most people miss. Pinterest is a strong fit for visual/Turkish design content.

**Google Trends API (official, alpha)** — UNVERIFIED specifics: reported ~1800-day (5yr) lookback, geo-level granularity, and 'consistently scaled' values (unlike the web UI's per-query 0-100 renormalisation, which makes cross-query comparison possible). Still alpha as of the last primary announcement I could reach; access is not guaranteed. Turkish (TR) geo support assumed but not confirmed.

**pytrends / unofficial Google Trends libraries** — Apache 2.0-ish but effectively unmaintained and chronically broken by Google endpoint changes and 429s. Scraping Trends is against Google ToS. Values are renormalised 0-100 per request so you cannot compare across queries without an anchor term. Use only as a stopgap until the official alpha lands.

**Google Search Console API (Search Analytics)** — Quotas: Search Analytics 1,200 QPM per site, 1,200 QPM per user, 40,000 QPM and 30M QPD per project. URL Inspection 600 QPM / 2,000 QPD per site. Other resources 20 QPS / 200 QPM per user. Historical data limited to ~16 months in the UI/API — export daily to your warehouse to build a longer series. Row limit 25,000 per request, paginate with startRow. Data is anonymised/sampled for low-volume queries.

**Bing Webmaster Tools API** — One API key per user, not per site. Still documented and live in 2026 though the docs are stale (last substantive update 2019-2022). Endpoints include GetQueryStats, GetPageStats, GetRankAndTrafficStats, plus SubmitUrl for indexing. Meaningfully relevant in Turkey where Bing share is non-trivial and it also feeds ChatGPT/Copilot search surfaces. Quotas not published — self-throttle.

**PostHog (Cloud free tier + OSS self-host)** — The 1M free events/month is far beyond what a solo operator will use — realistically permanently free. Self-hosted K8s support has been SUNSET; only docker-compose hobby is maintained and it wants a beefy box (ClickHouse+Kafka+Postgres). Query API caveat is important: PostHog explicitly states /query is 'not a supported export mechanism', 100 rows default / 50,000 max, no OFFSET pagination with personal API keys (HTTP 400) — use keyset pagination on timestamp, or batch exports for bulk.

**PostHog MCP server** — Requires enabling AI data processing in org settings. This is the single fastest way to give your command-center agent read access to real product analytics without writing a connector. Scope the personal API key tightly (Query Read only).

**Umami** — MIT is the most permissive licence in this category — no AGPL contamination worries. Requires PostgreSQL 12.14+. Full feature and API parity self-hosted, unlike Plausible. Very light: runs happily on a €5 VPS or Vercel + Neon free tier. No session replay or funnels-depth compared to PostHog.

**Plausible Community Edition** — DISQUALIFYING for your use case: the Stats API is a Business-plan cloud feature and is explicitly NOT available in Community Edition. CE also lacks funnels, user journeys and ecommerce revenue goals, has only basic bot filtering, ships long-term releases twice a year, and excludes the Data Studio connector. Cloud Stats API rate limit is 600 req/hour with 11 metrics and 60+ dimensions. You'd have to pay for Business cloud to get programmatic access.

**Matomo (self-hosted)** — The Reporting API is genuinely the most complete of the OSS set — every dashboard widget is an API method. Downside: PHP/MySQL, heavier ops, slower on large datasets, dated UX. Free Marketplace plugins are GPL v3 unless noted. Do NOT enable 'only allow secure requests' for tokens used in GET tracking requests.

**Rybbit** — All features ship in the open-source version including session replay and funnels — unusual and notable. ClickHouse backend means it scales far past your needs but also means heavier infra than Umami. AGPL-3 is fine for personal use but would matter if you ever productise the suite. Younger project — less battle-tested.

**OpenPanel** — Stack: Postgres (metadata) + ClickHouse (events) + Redis (cache/pubsub). API surface is less documented than PostHog's or Umami's — verify the read/query endpoints before committing an agent to it. AGPL-3.0.

**Countly Community Edition** — The modified AGPL Section 7 adds attribution/branding conditions — read it before embedding. Node.js + MongoDB stack. Heavier and more mobile-app oriented than you need. Actively maintained (27k+ commits).

**DuckDB** — Columnar-vectorised engine, ACID via bulk-optimised MVCC. Perfect fit for 'thousands to millions of rows of content performance data queried by an LLM'. Single-writer: one process holds the write lock, but you can open unlimited read-only connections concurrently — so run your ingestion job and your agent's read connection separately. Store the .duckdb file in the repo directory (git-ignore it, back up to object storage).

**MotherDuck / DuckDB MCP server** — Explicitly supports local files, not just MotherDuck cloud — that's the key detail. Use read-only for the analyst agent and a separate write connection for your ingestion jobs. Works with Claude Code (`claude mcp add`), Claude Desktop, Cursor, VS Code, Codex.

**SQLite** — Fine for your operational/state data (post queue, schedule, brand assets, agent run logs) but the wrong shape for analytical aggregation over time series — no columnar storage, no vectorised execution, weak window/aggregate performance at scale. Best used ALONGSIDE DuckDB: SQLite for app state, DuckDB for analytics (DuckDB can read SQLite files directly via sqlite_scanner).

**PGlite** — Supports many Postgres extensions including pgvector and PostGIS — pgvector in-browser is interesting for semantic search over your brand/content corpus. BUT: single user/connection only, and it's a row-store, so it's not an analytics engine. Great for a local-first command-center UI that needs real SQL client-side; not your warehouse.

**ClickHouse (single node)** — Massive overkill for thousands of rows: it wants several GB of RAM and real ops attention for a workload DuckDB handles in a single file. It IS what powers Rybbit, OpenPanel and PostHog under the hood — so you get it transitively if you self-host those. clickhouse-local/chDB is the interesting middle ground (DuckDB-like ergonomics, ClickHouse engine).

**Postgres + TimescaleDB** — The TSL licence permits free use but prohibits offering it as a managed DBaaS — irrelevant for personal use. Best choice ONLY if you already run Postgres for the app and want one database for everything. Continuous aggregates are genuinely nice for daily-rollup content metrics. But it's a server to maintain.

**dlt (data load tool)** — This is the missing piece most people skip. Handles incremental loading, schema evolution, and state — so your daily 'snapshot IG insights before the 90-day window eats them' job is ~30 lines instead of 300. Explicitly designed to be written by coding agents, so Claude can generate your Instagram/LinkedIn/YouTube pipelines. Pairs perfectly with DuckDB as destination.

**Evidence.dev** — MIT — the friendliest licence of any BI tool here. Native DuckDB support (ships a sample .duckdb). Because dashboards are just Markdown+SQL files in your repo, an agent can WRITE new dashboard pages as a normal file edit — this is uniquely well-suited to an agentic command center. No server to run. Downside: no ad-hoc drag-and-drop exploration for a human.

**Metabase (Open Source Edition)** — OSS edition includes unlimited questions/dashboards/users, SQL editor and AI question-asking. Advanced/interactive embedding is Pro+ (from ~$575/mo) — static/signed embedding availability in OSS is UNVERIFIED. AGPL matters if you ever ship the suite. Connects to DuckDB via a community driver (not first-party). JVM, ~1GB RAM.

**Grafana OSS** — Licence changed from Apache 2.0 to AGPL-3.0 in 2021 — check LICENSING.md if you ever redistribute. Dashboards-as-JSON means an agent can generate them, but the JSON is verbose and painful compared to Evidence's Markdown. No first-party DuckDB datasource (community plugin only). Its real strength is alerting — useful for 'tell me when a post breaks out'.

**Apache Superset** — Apache 2.0 is a real advantage over Metabase's AGPL and Grafana's AGPL if you ever commercialise. But it's a Python/Flask/Celery/Redis/metadata-DB stack — by far the heaviest thing to operate here for one person. Chart quality is excellent.

**Lightdash** — The MCP server plus a governed semantic layer is conceptually the strongest fit for 'LLM agent asks questions about my metrics' — the agent queries defined metrics rather than raw tables, which drastically reduces hallucinated SQL. Cost: you must maintain dbt or YAML metric definitions. Overkill unless you enjoy that discipline.

**Observable Framework** — Similar philosophy to Evidence but JavaScript-first rather than SQL-first, with far more control over visual design — relevant given you care about brand and visual identity. Data loaders can be any language, so a Python script that hits the Instagram API is a legitimate loader. Instant page loads because everything is precomputed at build.

**Cube (Cube Core)** — Sits between your DuckDB/Postgres and both your dashboards and your agent, so 'engagement_rate' means one thing everywhere. The Postgres-wire SQL API means any Postgres MCP server can talk to it. MCP support is emerging but not primary-confirmed. Adds a moving part — only worth it if you have >10 derived metrics.

**Tremor / Recharts / visx** — UNVERIFIED licences (not re-checked from primary this session, though all three are historically MIT). Tremor gives you dashboard-shaped primitives (KPI cards, bar lists) fastest; Recharts is the pragmatic middle; visx is D3 primitives for full brand control. If the command center is a Next.js app, this beats embedding a BI tool in an iframe — and an agent can generate these components directly.

**Dub.co** — Major 2026 change: Dub removed the free tier and moved upmarket — the old 'free 25 links' plan is gone. Core is AGPLv3 with a commercial licence for enterprise features; self-hosting IS supported and documented. Analytics run on Tinybird (ClickHouse), so self-hosting means bringing your own Tinybird account or ClickHouse — not a trivial lift. $90/mo is indefensible for a personal project.

**Shlink** — Records per-visit data with GeoLite2 geolocation (MaxMind attribution required), referrer, user agent, and UTM-style tag support. Runs on PHP 8.4/8.5 with MySQL/MariaDB/Postgres/SQL Server/SQLite — SQLite mode makes it genuinely trivial to run. MIT means no AGPL concerns. Its API is well-documented enough for an agent to both create links and pull visit stats.

**YOURLS** — Older and simpler than Shlink; analytics are basic (click counts, referrers, country) and the API is signature-based rather than modern REST. Huge plugin ecosystem. Choose it only if you already run a LAMP box. Shlink's API is materially better for agent consumption.

**Serper.dev** — The autocomplete endpoint is an underrated free-ish keyword-research source — great for Turkish long-tail discovery. Scraping-derived data, so the usual grey-area ToS caveat applies to Google's terms, not Serper's. Latency ~1-2s. TR geo/hl parameters supported.

**SerpApi** — Notably includes 'U.S. Legal Shield' — SerpApi indemnifies against scraping claims, which no cheaper competitor offers. 3-10x Serper's price. The 250/month free tier is enough for weekly keyword checks.

**DataForSEO** — The only source in this list that gives real Google Ads keyword search volume, CPC and competition for Turkish keywords at commodity prices — that's its unique value. Also proxies Google Trends. Task-based async model needs a queue in your pipeline. $50 goes a very long way at a solo scale.

**Exa** — The recurring $10/month free allowance is unusual and effectively free for personal research volumes. Semantic search finds conceptually similar content (great for 'who else writes about this in Turkish') where keyword SERPs fail. 'Monitors' can watch a query over time — a cheap competitor-tracking primitive.

**Tavily** — 1,000 free credits/month is the most generous free allowance of the agent-search APIs and renews monthly. Returns LLM-ready cleaned content rather than raw HTML, which saves tokens. Crawl and Map are useful for ingesting a competitor's whole site once.

**Reddit Data API** — Register an OAuth app and set a descriptive User-Agent or you will be blocked. Reddit aggressively rate-limits and blocks datacentre IPs for unauthenticated access. The 'non-commercial' boundary is ambiguous for a solo operator marketing their own SaaS — read the Data API Terms yourself before scheduling anything. Turkish-language subreddits are thin; value is mainly for global SaaS/dev audience research.

**RSSHub** — Has routes for Twitter/X, Instagram, YouTube, TikTok, Telegram, Bilibili, Weibo and thousands of sites. This is the single best FREE social-listening and competitor-tracking primitive: point RSSHub at competitors' profiles, poll the feeds on a cron, and pipe new items into DuckDB for your agent to summarise — no platform API keys, no per-call cost. Caveat: many social routes are unofficial scrapes that break, and some need cookies; self-host rather than trusting a public instance with credentials. AGPL-3.0.

**changedetection.io** — Apache-2.0 is the friendliest licence in the listening category. The OpenAPI spec means you can generate a client (or an MCP wrapper) so your agent can add/remove watches itself — e.g. 'start watching this competitor's pricing page'. Supports CSS/XPath selectors and optional browser rendering for JS-heavy pages. Webhook notifications drop straight into your pipeline.

**Ayrshare** — Solves the single hardest problem here — it already holds the LinkedIn, Instagram and TikTok partner approvals you would struggle to obtain solo. But $149/mo minimum for one profile is roughly $1,800/yr for a personal project, and you're renting access to your own data. The 28-day no-card trial on Launch is worth using to see exactly which metrics each network really returns before you build your own connectors.

**Google Analytics 4 Data API** — UNVERIFIED exact 2026 quota figures. Not open source and not privacy-friendly (cookie consent obligations under KVKK/GDPR apply in Turkey), but it's free, has a solid API, and 14-month default data retention means you should export to DuckDB anyway. Include it only if you already run GA4 on your product sites.

**Cloudflare Web Analytics + GraphQL Analytics API** — If your sites already sit behind Cloudflare this is genuinely zero-marginal-cost, cookieless, no consent banner, and server-side (ad-blocker proof) for proxied traffic. The GraphQL API is well-suited to an agent that can read a schema. Retention on the free plan is short — snapshot daily.

**Tinybird** — This is what Dub.co runs its click analytics on. The 'write a SQL query, get a documented REST endpoint' model is exceptionally agent-friendly — your dashboard and your agent hit the same endpoint. Worth evaluating as a hosted alternative to running ClickHouse yourself IF you outgrow DuckDB, which at thousands of rows you will not.

### Öneriler

- Make DuckDB (single .duckdb file in the repo, git-ignored, backed up to object storage) your metrics warehouse and expose it to Claude via the MIT-licensed mcp-server-motherduck in read-only mode, with a separate write connection reserved for ingestion jobs — at thousands of rows this gives an LLM agent full SQL over every content metric with literally zero servers to operate.
- Treat every platform API as a lossy 90-day window and build a daily dlt (Apache 2.0) snapshot job per platform before anything else: Instagram user insights vanish after 90 days, Facebook Page insights after 2 years with a 90-day query cap, Threads has no data before 2024-04-13, and Google Search Console only keeps 16 months — the warehouse is not a nice-to-have, it is the only copy that survives.
- Apply for LinkedIn Community Management API access immediately, and in parallel create a LinkedIn Company Page for your products so that organizationalEntityShareStatistics is available as a fallback if r_member_postAnalytics is denied — this is the longest-lead-time dependency in the entire build and everything else can proceed while it is pending.
- Use PostHog Cloud's free tier (1M events, 5K session replays, 1M feature-flag requests per month) plus its free official MCP server for product analytics rather than self-hosting anything — the free allowance is orders of magnitude above a solo operator's volume, self-hosted Kubernetes support has been sunset, and the MCP server gives your agent HogQL access in a single config block.
- Do not use Plausible Community Edition: the Stats API is explicitly a paid Business-plan cloud feature and is absent from CE, which makes it useless to an agentic pipeline — choose Umami instead, which is MIT-licensed and ships its complete API in the self-hosted build with genuine feature parity.
- Build the command-center dashboard as code with Evidence.dev (MIT, static output, native DuckDB) or Observable Framework rather than embedding a BI tool, because Markdown-plus-SQL dashboard files live in your repo as ordinary text that a coding agent can author and revise — and pull in Grafana only for threshold alerting on breakout posts.
- Skip Dub.co's hosted product now that it has removed its free tier and starts at $90/month, and self-host Shlink instead: MIT-licensed, a well-documented REST API your agent can call to both mint UTM-tagged links and read per-visit geo data, and it runs on SQLite so there is effectively no operational burden.
- Cover trend and competitor intelligence with the free-tier stack rather than paid social listening: self-host RSSHub (AGPL-3.0) to turn competitor social profiles into pollable RSS, self-host changedetection.io (Apache-2.0, full REST API with OpenAPI spec) to watch competitor pricing and launch pages, and pipe both into DuckDB for the agent to summarise weekly.
- Deposit the $50 minimum at DataForSEO once — it is the only affordable source of real Google Ads search volume and CPC for Turkish keywords, which is the single hardest data point to get for Turkish-language content planning, and $50 lasts an extremely long time at solo volumes.
- Default your agent's web research to Tavily's renewing 1,000 free credits per month, escalate to Exa for semantic discovery and its Monitors feature (Exa gives $20 signup credit plus $10 free every month thereafter), and keep SerpApi's free 250 searches/month in reserve for the occasional raw SERP check — this combination costs zero and covers the whole research surface.
- Prioritise YouTube and Threads as analytics-rich channels and treat X as write-mostly: YouTube Analytics costs 1 quota unit per query against a 10,000-unit daily allowance with deep history, Threads insights are free with no App Review gauntlet, while X now charges per read and reportedly adds a surcharge for posts containing links — which is precisely what content marketing does.
- Define your derived metrics (engagement rate, cost per view, channel velocity) once in plain SQL views inside DuckDB from day one, and only graduate to a real semantic layer like Cube or Lightdash if you later find the agent and your dashboards disagreeing about what a metric means — the semantic layer is the correct long-term pattern but premature at this scale.


### Riskler

- Meta's metric churn is the top structural risk: `impressions` was deprecated in v22 and removed in v23, reel plays were folded into `views`, and Meta versions the Graph API quarterly with roughly a two-year sunset — any dashboard you build will silently break unless you pin an API version, monitor the changelog, and keep raw JSON responses alongside parsed metrics so you can re-derive history after a schema change.
- The 90-day Instagram insights retention window means a single extended outage of your snapshot job causes permanent, unrecoverable data loss — there is no backfill endpoint. Your ingestion cron needs its own alerting, and you should retain raw API payloads, not just parsed rows.
- LinkedIn's r_member_postAnalytics permission sits behind Community Management API partner approval that is routinely denied to individual developers with no product to show; if you are rejected, personal-profile LinkedIn analytics has no legitimate API path and your only options are manual CSV export or paying roughly $1,800/year for Ayrshare.
- TikTok's Research API explicitly excludes creators, advertisers and commercial users, and eligibility narrowed further in 2026 — any plan that assumes TikTok trend or competitor data via official channels will fail, and third-party scraping providers carry ToS and account-ban exposure.
- X's shift to credit-based pay-per-use removes the cost ceiling that a flat subscription provided: without a hard spend cap enforced in your own code, a looping agent or a retry storm can burn real money, and the reported surcharge on link-containing posts penalises exactly the posting pattern a content pipeline produces.
- Licence contamination is a live concern if the Creative Suite ever stops being personal-only: Grafana (AGPL-3.0-only), Metabase OSS (AGPL), Rybbit (AGPL-3), OpenPanel (AGPL-3.0), RSSHub (AGPL-3.0), Countly (AGPL-3.0 with a modified Section 7 adding attribution conditions) and Dub core (AGPLv3) all impose source-disclosure obligations on network-accessible modified versions — the MIT/Apache path (DuckDB, Umami, Evidence, Shlink, changedetection.io, Superset, dlt, Cube) keeps that door open at no functional cost.
- PostHog explicitly warns that its /query endpoint is not a supported export mechanism, caps results at 50,000 rows, rejects OFFSET pagination for personal API keys with HTTP 400, and reserves the right to rate-limit or reject export-shaped queries without notice — an agent that naively paginates a large export will be throttled, so use keyset pagination on timestamp or batch exports.
- Meta's Business Use Case rate limit is proportional to your own engagement (4,800 calls per 24h multiplied by impressions for Instagram, or by engaged users for Facebook Pages), which means a new or low-traffic account has a very small call budget precisely when you are building and debugging the integration — cache aggressively and honour the X-Business-Use-Case-Usage header.
- Pinterest Trial access is capped at 1,000 requests per DAY across all endpoints combined, which is not enough to run even a modest daily pipeline; you must complete the review process for Standard access before Pinterest is usable at all, and that review takes time.
- Unofficial Google Trends scraping via pytrends violates Google's terms, breaks frequently, and returns values renormalised 0-100 per request so they cannot be compared across queries without an anchor term — building content strategy on those numbers produces confidently wrong conclusions.
- Under Turkish KVKK (and GDPR for EU visitors) self-hosted cookieless analytics such as Umami, Plausible CE or Cloudflare Web Analytics materially reduces your consent-banner and data-processing obligations compared to GA4 or PostHog Cloud; routing personal data to US-hosted SaaS analytics adds a cross-border transfer question you would otherwise avoid entirely.
- Third-party unofficial API resellers (SociaVault, Phyllo, KeyAPI, Data365 and similar) that promise cheap TikTok, Instagram or X data almost always operate through scraping or pooled credentials in breach of platform terms; using them risks having your linked social accounts actioned, which for a personal brand is a far larger loss than the analytics were worth.
