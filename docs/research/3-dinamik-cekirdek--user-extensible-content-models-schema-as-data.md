## Özet

The founder's constraint rules out almost every mainstream CMS, and the reason is sharper than it first looks. There are two separate freedoms — *runtime schema editing* and *git-as-truth* — and essentially no single tool gives both. Config-as-code CMSs (Payload v3, Keystone 6, Keystatic, TinaCMS) are git-native but the schema is TypeScript a developer writes: hard fail on requirement (a). Database CMSs (Directus, NocoDB, Teable, Baserow, Grist, Budibase) let a non-developer create entity types at runtime but the truth lives in Postgres, not the repo: hard fail on the repo-of-truth premise. Strapi v5 is a clean disqualification — its Content-Type Builder is documented "Available in Development environment only."

The resolution is to stop shopping for a CMS and treat the meta-model as the product. Store entity-type definitions as JSON Schema 2020-12 documents in YAML files in the repo (`/schema/entity-types/*.yaml`). Those files are data; the command center gets a schema editor that writes them and commits. Records become one markdown+frontmatter file each, validated against their type by Ajv. Everything queryable is a *derived* index (SQLite/PGlite) that is gitignored and rebuilt — this is what makes git-as-truth survive at 5000 records without binary bloat or merge hell.

The payoff is that one JSON Schema drives three surfaces: the editing form (react-jsonschema-form or JSONForms, both mature and permissive), build-time TypeScript (json-schema-to-typescript), and LLM structured output. That third one carries a verified trap: OpenAI's structured-output subset bans `allOf`, requires every field `required`, and mandates `additionalProperties:false`, so a ~100-line projection compiler from authoring schema to strict LLM schema is a real, mandatory component — not a detail.

Two 2026 licence facts matter. Directus left MIT for the Monospace Sustainable Core License, but its Open Innovation Grant makes self-hosting *fully free* under $5M revenue and 50 employees — Upcytech qualifies outright, and `/schema/snapshot?export=yaml` + `/schema/diff` + `/schema/apply` makes its schema git-exportable. That makes Directus the best optional accelerator, not the core.

**JSON Schema 2020-12** — VERIFIED from the spec site: '(t)he current version is 2020-12! The previous version was 2019-09.' No newer stable release as of 2026 — a stabilisation effort ('Moving Toward a Stable Spec', Jan 2025) is in progress but 2020-12 remains current. This stability is a feature: a schema format that has not churned in six years is the right thing to bet a decade-long knowledge model on. Use $id for versioned identity, $defs + $ref for shared field groups (address, provenance, era-tag), and allOf for entity-type composition (base-entity + vertical-specific mixin). unevaluatedProperties (2020-12) is what makes composition-based extensibility actually enforceable, which draft-07 could not do.

**Directus** — VERIFIED licence: repo LICENSE file is 'Monospace Sustainable Core License, Version 1.0' (MSCL-1.0-GPL), which restricts competing use, forbids circumventing the licence key, and grants an irrevocable GPL-3.0 licence on the fourth anniversary of initial availability — a delayed-open-source clause. VERIFIED pricing: 'Organizations under $5M in annual revenue and fewer than 50 employees qualify for fully permissive access to Directus at no software cost. Self-hosted is completely free.' Upcytech qualifies with enormous headroom. 37.4k stars. CRITICAL CAPABILITY, VERIFIED from the schema API docs: GET /schema/snapshot (with export=json|yaml|csv|xml), POST /schema/diff (mirror or merge mode — merge is additive-only), POST /schema/apply. That triple is exactly a git-friendly schema-as-data workflow: snapshot to YAML, commit, diff, apply. Extensions cover hooks, endpoints, operations, interfaces, displays, layouts, panels, modules, themes. THE CATCH: schema exports to git, content does not — records live in Postgres. Using it as the core would abandon the repo-of-truth premise. Correct role: a satellite for any high-volume tabular data (prospect lists, ad-performance rows) with a scheduled YAML export back into the repo.

**json-schema-to-typescript** — VERIFIED: MIT, 3.3k stars, 609 commits, actively maintained, used by Amazon, Microsoft, Mozilla and Webpack. **OpenAI Structured Outputs JSON Schema subset** — VERIFIED and load-bearing. Supported types: string, number, boolean, integer, object, array, enum, anyOf. Supported string keywords: pattern, format (date-time, time, date, duration, email, hostname, ipv4, ipv6, uuid). Numbers: multipleOf, maximum, exclusiveMaximum, minimum, exclusiveMinimum. Arrays: minItems, maxItems. UNSUPPORTED KEYWORDS: 'Composition: allOf, not, dependentRequired, dependentSchemas, if, then, else'. REQUIRED-FIELD RULE: 'All fields or function parameters must be specified as required' — optionality must be emulated with a union against null. OBJECT RULE: 'additionalProperties: false must always be set in objects.' $ref IS supported via $defs including recursive '#'. LIMITS: up to 5000 object properties total, 10 levels of nesting, 120,000 characters across all property/definition/enum/const names, up to 1000 enum values. Fine-tuned models additionally lose string/number constraints, patternProperties and array item constraints. CONSEQUENCE: the authoring schema will use allOf for entity composition and optional fields for sparse data — both illegal here. A projection compiler must inline allOf into flat properties, mark every property required, wrap genuinely optional fields as anyOf [T, null], and force additionalProperties:false recursively. Roughly 100 lines, fully testable, and it is the single most important piece of glue in the design.

**Markdown + YAML frontmatter, one file per record** — Reasoned recommendation, grounded in the verified storage models of Keystatic, TinaCMS and Pages CMS, which all independently converged on it. Why it wins at this scale: line-level git diffs make every change to the brand DNA reviewable; merge conflicts are confined to a single record and, for a solo operator with sequential edits, are close to nonexistent; the founder can edit any record in any text editor with no running service; and agents can read records directly with zero query layer. Repository size stays trivial — 5000 records at ~4KB averages ~20MB of highly compressible text. Directory layout carries meaning: /content/<entity-type>/<slug>.md. Prose-bearing records (positioning statements, case studies, persona narratives) use markdown body plus frontmatter; purely structural records (channel definitions, model routing policy) are better as standalone .yaml with no body. The one real weakness is querying, which the derived-index item below resolves.

**Derived index (SQLite or PGlite), gitignored** — VERIFIED for PGlite: 'a WASM Postgres build packaged into a TypeScript client library' running in browser, Node.js, Bun and Deno; ~3MB gzipped; no dependencies; 15.8k stars; dual-licensed Apache 2.0 and PostgreSQL Licence; single-user/single-connection mode. VERIFIED persistence options: in-memory, IndexedDB in browser, filesystem in Node/Bun/Deno. VERIFIED extensions: pgvector and PostGIS confirmed supported — pgvector matters directly, since it lets the same index serve both structured filtering and semantic retrieval for agent context assembly. UNVERIFIED: dump/load file functionality was not detailed in the fetched README; confirm before relying on snapshot/restore. THE ARCHITECTURAL RULE: this index is a pure function of the markdown corpus, so it is disposable and MUST be gitignored. That single discipline is what lets you keep SQL power while avoiding every binary-in-git pathology. Plain better-sqlite3 with FTS5 is the lower-risk alternative if pgvector is not needed on day one.

**SQLite committed to git** — Reasoned judgement, stated honestly as such: the SQLite page fetched documents SQLite's merits as an application file format (about 20% smaller than individual files for 10KB blobs, ~35% faster reads/writes) but says nothing about version control, so the VC argument below is analysis rather than citation. The failure modes are structural, not incidental: git sees an opaque binary, so `git diff` and code review of a brand-DNA change are impossible; any two divergent edits produce a whole-file conflict git cannot resolve; and because SQLite rewrites pages on write, every commit stores a fresh near-full copy, so repo size grows with the number of edits rather than the amount of data. Over a multi-year, many-regeneration lifetime that is exactly the wrong growth curve. The same objection applies to Grist .grist files. Use SQLite enthusiastically — as the gitignored derived index.

**Dolt** — VERIFIED: 'a SQL database that you can fork, clone, branch, merge, push and pull just like a Git repository'; Apache License 2.0; 24.2k stars; 859 forks; 31,502 commits; supports MySQL up to 8.4; actively developed alongside DoltHub, DoltLab and Hosted Dolt. VERIFIED schema-evolution capability, which is the relevant part: branches can carry schema modifications such as adding a column, be tested in isolation, and merge back to main without conflicts. VERIFIED diff tooling: dolt_diff_<tablename> system tables expose changes between commits, branches and individual cells, tracking 'when, how, and why each cell in your database changed over time'. That cell-level history is a genuinely superior answer to requirement (b) — brand-era regeneration becomes a branch, and old assets keep referencing old commits natively. THE COST: it is a running MySQL server, so the working tree is not human-readable, the founder cannot open a record in a text editor, and agents need a SQL client rather than a file read. Apache-2.0 with a real company behind it makes this the safest of the exotic options. Revisit if record count ever passes ~50,000.

**Schema evolution: additive-default with lazy migration** — Synthesised from verified migration models. Directus offers the closest primitive: POST /schema/diff supports a 'merge' mode explicitly restricted to additive changes, versus 'mirror' mode for all operations — the platform itself encodes the additive-safe/destructive-unsafe distinction, which is strong evidence the rule is correct. Payload's split is the other data point: Drizzle push auto-syncs in development while production requires committed migration files, with an explicit warning never to mix the two. THE RULES: (1) every entity-type YAML carries schemaVersion, and every record's frontmatter records the schemaVersion it was written under; (2) additive changes — new optional field with a default — need no migration, and old records simply read with the default; (3) on read, if record.schemaVersion is behind, apply registered up-migrations in memory and persist on next write (lazy migration), so nothing ever requires a big-bang rewrite; (4) destructive changes — rename, delete, retype — require a committed codemod at /schema/migrations/<type>/NNNN-description.ts that maps over frontmatter with gray-matter, producing a reviewable git diff across every touched record; (5) prefer retired:true on a field over deletion, so historical records stay readable forever. Rule 5 is what makes requirement (d) survivable: a total company transformation retires old types rather than destroying old truth.

**Era-tagging via content-addressed brand DNA versions** — Design derived from a verified Pages CMS property: its .pages.yml config is read 'per repository AND per branch', proving that branch-scoped schema is a real, shipped pattern rather than a theoretical one. THE DESIGN: each brand-discovery run writes an immutable era record at /eras/<ulid>.md capturing the run's inputs, model versions, prompts, cost and resulting DNA, plus the git commit SHA of the schema registry at that moment. Every generated asset's frontmatter carries era_id. Because era records are immutable and append-only, 'run it again' creates a new era and never mutates old ones, so an Instagram post from 2026 keeps pointing at the 2026 DNA even after three regenerations — old assets stay correctly tagged with zero extra bookkeeping. A pointer file (/eras/current) names the active era, making rollback a one-line change. Ajv validates era records like any other entity, so the era type itself is user-extensible. This costs no new dependency, which is the point: because truth is immutable files in git, versioning the brand engine reduces to a naming convention plus a foreign key.

### Öneriler

- BUILD THE META-MODEL, DO NOT BUY A CMS. No reviewed tool provides both runtime schema editing and git-as-truth — that combination does not exist commercially. Store entity types as JSON Schema 2020-12 documents in YAML at /schema/entity-types/*.yaml. These files ARE the data the founder edits. The command center gets a schema editor that writes and commits them. This is roughly 2-3 weeks of work and permanently satisfies requirement (a) with no vendor able to revoke it.
- ADOPT THE FOUR-LAYER STACK: (1) schema registry — JSON Schema YAML in git; (2) records — one markdown+frontmatter file per record under /content/<entity-type>/<slug>.md; (3) validation — Ajv at runtime against the registry, json-schema-to-typescript at build for compile-time types; (4) query — a gitignored SQLite/PGlite index rebuilt from the files. Layer 4 being disposable is the discipline that makes files-as-truth scale to 5000 records without binary bloat.
- WRITE THE SCHEMA PROJECTION COMPILER EARLY — it is the highest-value ~100 lines in the system. One authoring schema must project to three targets: the RJSF form schema, the generated TypeScript, and the strict LLM output schema. The LLM projection is non-optional because OpenAI's subset bans allOf, requires every field to be `required`, and mandates additionalProperties:false. Inline allOf, force all-required, wrap optional fields as anyOf [T, null], recurse additionalProperties:false. Unit-test it against every entity type; it is where silent breakage will otherwise live.
- USE react-jsonschema-form WITH THE shadcn THEME as the editing UI. Apache-2.0, 15.9k stars, actively maintained, ten theme packages. This delivers the headline property: the founder adds a field to a YAML file and the editing form grows that field with zero code written. Confirm draft 2020-12 keyword coverage before using unevaluatedProperties in any schema that must render as a form — RJSF's draft support was not verifiable from the repo page.
- MAKE STORAGE FORMAT FOLLOW RECORD SHAPE. Prose-bearing records (positioning statements, case studies, persona narratives, post drafts) get markdown body plus frontmatter. Purely structural records (channel definitions, model routing policy, budget caps) get standalone .yaml with no body. ### Riskler

- THE GENERATED-TYPES ILLUSION. json-schema-to-typescript verifiably drops every constraint TypeScript cannot express — pattern, format, minimum/maximum, multipleOf, uniqueItems, minProperties/maxProperties, dependencies, not. Generated types cover SHAPE ONLY; Ajv must cover CONSTRAINTS. If code trusts the types alone, invalid data flows through silently. Worse: because schemas change at runtime but types are generated at build time, a schema edited after the last build produces types that are quietly a lie. Mitigation: application code must be written against the generic meta-model (typed field accessors returning unknown, narrowed by validation), with generated types used only in hand-written specialised views.
- oneOf IS TREATED AS anyOf by json-schema-to-typescript, so discriminated unions do not narrow correctly. Any entity type modelling variants (a Product that is either SaaS or bespoke, say) will produce a union TypeScript cannot discriminate. Mitigation: add an explicit literal discriminant property (kind: 'saas' | 'bespoke') to every variant schema rather than relying on oneOf semantics.
- LLM SCHEMA DRIFT IS SILENT AND WILL BITE. The projection from authoring schema to OpenAI's strict subset is lossy in ways that produce no error — an allOf that fails to inline, a nested object missing additionalProperties:false, a schema that quietly crosses the 5000-property or 10-level-nesting ceiling. The API rejects some of these loudly and degrades on others. Mitigation: snapshot-test the projected schema for every entity type in CI, and assert the property count and nesting depth explicitly.
- DIRECTUS LICENCE IS A MOVING TARGET. The switch from MIT to the Monospace Sustainable Core License is recent, and the Open Innovation Grant is a commercial policy — not an irrevocable licence grant — that can be narrowed at any time. The MSCL itself forbids circumventing licence-key functionality, so key checks are load-bearing code. There is a delayed GPL-3.0 grant on the fourth anniversary of each release, which caps the downside, but a version released today is not GPL until 2030. Mitigation: the satellite-only recommendation means walking away costs a service, never the data. Re-read the grant terms annually.
- BUS FACTOR ON THE ATTRACTIVE SMALL TOOLS. Sveltia CMS (2.7k stars) appears near-solo; Velite (805 stars) is single-maintainer; Front Matter CMS's maintainer has publicly stated that 'major changes will only happen if there's a personal reason, a company commitment, or significant community support'; TerminusDB has changed hands to 'new maintainers'. Each is individually defensible; depending on several compounds the risk. Mitigation: the file-based architecture means every one of these is a replaceable editing surface over data you already own — never let one become a storage dependency.
- MERGE CONFLICTS ARE LOW-RISK TODAY AND RISE WITH AGENT CONCURRENCY. One markdown file per record makes conflicts rare for a solo operator editing sequentially. But agentic generation writing many records in parallel branches — or a full brand-era regeneration touching thousands of files at once — reintroduces them at scale. Mitigation: agents write to per-run branches, never to main directly; regeneration writes to a new era directory rather than mutating existing records; keep records small and single-purpose so conflicts stay confined.
- AGPL EXPOSURE IN THE MEMORY LAYER. Basic Memory and Teable's community edition are both AGPL-3.0. AGPL obligations attach on network use, not just distribution — so linking their code into a command center that is ever exposed beyond localhost creates a source-disclosure obligation. Mitigation: use them only as separate processes over HTTP or MCP, never as in-process libraries, and prefer the Apache-2.0/MIT options (Directus's grant, Grist core, Dolt, Cognee, RJSF) where a choice exists.
- ZOD'S REVERSE CONVERSION IS EXPERIMENTAL AND MUST NOT BE ON THE RUNTIME PATH. z.fromJSONSchema() is explicitly 'not considered part of Zod's stable API'. Any design that converts user-authored JSON Schema into Zod at runtime inherits that instability. Also note z.date() is unrepresentable in JSON Schema and throws by default — a trap in a content system. Mitigation: Ajv validates user-defined types directly from JSON Schema; Zod is confined to developer-authored schemas, using z.iso.datetime() strings rather than z.date().
- SCHEMA-EDITING POWER IS ALSO SCHEMA-BREAKING POWER. Giving a non-developer live authority to retype or delete fields means a single careless edit can invalidate thousands of records. Mitigation: the schema editor must run a dry-run validation of the proposed schema against the entire existing corpus before committing, report the exact count and identity of records that would fail, and refuse destructive changes unless an accompanying migration codemod is supplied.
- JSON SCHEMA EXPRESSIVENESS RUNS OUT AT RELATIONSHIPS. It validates documents, not graphs — it cannot express referential integrity, so a persona referencing a deleted vertical validates cleanly. As the ontology grows this gap widens. Mitigation: model references as typed string IDs with a custom x-ref-type annotation, and enforce integrity in a separate corpus-wide linter run in CI, not in the per-document validator.
