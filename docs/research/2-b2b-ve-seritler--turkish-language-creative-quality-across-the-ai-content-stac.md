## Özet

As of Aug 2026 the honest picture is: no Turkish-specific model is competitive for marketing copy. Every hard evidence source I could reach — the TR-MMLU paper (arXiv 2508.13044), the yerel.ai TurkishMMLU-Yüksel/Belebele-TR leaderboard, and the Trendyol/YTÜ-Cosmos model cards — puts the best open Turkish models (YTU-Turkish-Gemma-9b 62.3%, Trendyol-LLM-Asure-12B 62.2%) far below frontier general models (GPT-4o already scored 84.8% on TR-MMLU in 2025). Turkish local models are worth using only as cheap classifiers/rewriters, not as the copy voice. So: frontier LLM (Claude/Gemini/GPT) is the premium lane, and a large multilingual open model (Qwen3 / Gemma-based Turkish-Gemma-9b) is the free lane, with a mandatory deterministic Turkish post-check.

The single most actionable finding for a pipeline: LLMs systematically drop Turkish diacritics (ç ğ ı ö ş ü) in long-form generation, degrading past ~1500 words, and prompt instructions do NOT hold. ceaksan/turkish-diacritics (MIT) is a hunspell-based 4-layer validator with reported 90/90 detection and zero false positives on a reference file — wire it as a post-generation gate, not a prompt.

For images: do NOT let any model render Turkish text. Google only claims "multiple languages" for Nano Banana Pro with zero language list; Ideogram's own docs warn accented Latin "may have some difficulty being rendered correctly, if at all." Generate text-free imagery, then composite real text via Satori (MPL-2.0) or sharp+Pango with a latin-ext font.

Typography traps that will bite: Chrome has NO Turkish hyphenation dictionary (Firefox/Safari only, 19.4% global) — so Puppeteer/Chromium carousel rendering must hard-wrap manually; and JS uppercasing must use toLocaleUpperCase('tr') or "istanbul" becomes "ISTANBUL" not "İSTANBUL".

TTS free lane is settled: Chatterbox Multilingual v3 (Resemble AI, MIT, Turkish among 23 languages, zero-shot cloning). Avoid XTTS-v2 (CPML) and F5-TTS weights (CC-BY-NC) commercially. Premium lane: ElevenLabs v3 or Cartesia Sonic 3.5. Azure's Turkish voice roster is thin.

STT: Groq Whisper large-v3 at $0.111/hr is the cost-optimal lane; AssemblyAI publicly rates Turkish only "Good" (10–25% WER), so budget for human caption review.

Legal is now a live constraint, not theory: the amended Ticari Reklam ve Haksız Ticari Uygulamalar Yönetmeliği (Resmî Gazete 1 July 2026, in force 1 Aug 2026) adds Art. 18/8 and 27/12 covering AI-generated ad content and bans AI digital replicas of real people implying endorsement — fines up to ~8,635,800 TL for internet violations. KVKK principle decision 2026/347 (18 Feb 2026, published 24 Mar 2026) forces aydınlatma and açık rıza to be separate documents with separate declarations — directly affects any prospect/lead store. Good news for B2B: under Law 6563, prior consent is not required for commercial electronic messages to tacir/esnaf, but the opt-out right is absolute and İYS registration duties still apply.

**Claude (Anthropic API) — Turkish marketing copy** — Do NOT trust blog posts claiming specific 2026 model names/scores (see the sukruyusufkaya 'Claude Opus 4.7 = 87.3 composite' claim, which I could not corroborate anywhere). Always run the diacritics validator on output regardless of model.

**GPT-5 / OpenAI models for Turkish** — TR-MMLU's key methodological finding is that models with Turkish-aligned tokenization outperform — relevant because Turkish is agglutinative and token costs run ~30-40% higher than English for the same content.

**Gemini 3 Pro / Gemini API for Turkish** — Gemini 1.5 Pro scored 76.74% on TR-MMLU (2025 data) — behind GPT-4o/Claude at that time. Re-benchmark on your own Turkish brand-voice rubric before trusting.

**Trendyol-LLM-8B-T1** — Model card explicitly warns output 'should be considered as starting points or suggestions rather than definitive answers'. Trendyol-LLM-Asure-12B scores 62.2% TurkishMMLU-Yüksel / 86.6% Belebele-TR on the yerel.ai leaderboard — best-in-class for Turkish OSS but ~22 points behind GPT-4o's TR-MMLU.

**YTU-CE-Cosmos Turkish models (Turkish-Gemma-9b, Turkish-Llama-8b, ModernBERT-TR family)** — The 0.1B ModernBERT-TR embed/reranker pair is genuinely the right free-lane choice for retrieving Turkish brand-knowledge chunks — far better than a multilingual generic embedder and cheap enough to run on CPU. modernbert-tr-guardrail is a free pre-publish safety gate.

**yerel.ai Turkish LLM leaderboard (TurkishMMLU-Yüksel + Belebele-TR)** — Note Qwen 2.5 7B (generic, no Turkish tuning) at 53.7% sits above several Turkish-specific models. That is the strongest argument that 'Turkish-specific' is not automatically better for Turkish.

**TR-MMLU benchmark** — Key finding to quote in sales decks: models with Turkish-aligned tokenization significantly outperform, because Turkish is agglutinative. This also means your token budget for Turkish is materially higher than English — build that into the cost estimator.

**OpenLLM Turkish Leaderboard (malhajar) v0.2** — Listed for completeness because it is the historically canonical Turkish leaderboard. Verify liveness before relying on it.

**ceaksan/turkish-diacritics (Turkish diacritics validator)** — Evidence: 201 real blog posts tested, 4.81s avg/file, zero timeouts, 90/90 detection on a reference file with 90 known errors, zero false positives. The author's key claim is that prompt-engineering the fix FAILS — 'the model gradually disregards this instruction during long-form generation', with systematic degradation past ~1500 words. Catches e.g. 'ozellik'→'özellik'. It deliberately skips context-dependent homographs. Wire it as a hard gate before anything enters the human approval queue, on BOTH free and premium lanes.

**Nano Banana Pro (Gemini 3 Pro Image)** — CRITICAL CAVEAT: Google publishes NO list of supported languages for in-image text. The only worked examples are English and Korean. There is no published evidence anywhere I could find that ğ ı İ ş are rendered correctly at small sizes. Treat every Turkish word it renders as a defect until a human confirms. Your pipeline should default to text-free generation.

**Ideogram (v3/v4) text rendering** — Direct quote surfaced from Ideogram's prompting docs: text 'that you would like to be written using a non-Latin alphabet or accented Latin characters may have some difficulty being rendered correctly, if at all.' Ideogram 3.0 claims 'improved handling of non-Latin scripts, accented characters', but that is marketing, not a Turkish guarantee. This is the single clearest primary-source confirmation that the Turkish-text-in-image failure mode is real and vendor-acknowledged.

**Satori (Vercel)** — Constraints to design around: TTF/OTF/WOFF only (NOT WOFF2 — so subset to WOFF or TTF); kerning, ligatures and other OpenType features are NOT supported; no RTL; CSS subset only (no calc(), no z-index, no 3D transforms, no currentColor except on `color`). Supports a `lang` attribute per locale with matching fonts. MPL-2.0 is file-level copyleft — safe to use as a dependency in closed-source software.

**sharp + Pango text compositing** — Caveats: composited images must be the same size or smaller than the base; set `density` above the 72 DPI default when rasterising SVG or your Turkish text will be soft at 1080x1350. Set `rgba: true` if you use colour emoji or advanced Pango markup. Using `fontfile` with an absolute path is the reliable way to guarantee the ğ/ı/İ/ş glyphs are the ones you shipped.

**Google Fonts metadata endpoint (latin-ext filter)** — WHY latin-ext specifically: ç, ö, ü live in the basic Latin-1 range and almost every font has them — so a font can LOOK Turkish-ready and still fail. ğ, ş, ı and İ are the ones that live in latin-ext (Latin Extended-A). Always render a proof string containing 'ĞÜŞİÖÇ ğüşıöç Iı İi' when you add a font. Confirmed families carrying latin-ext include Albert Sans, Alegreya Sans, Afacad, Advent Pro, Akshar, Alata and many more; verify per-family from the JSON rather than trusting a blog list.

**String.prototype.toLocaleUpperCase('tr') / toLocaleLowerCase('tr')** — MDN's own example: 'istanbul'.toLocaleUpperCase('en-US') === 'ISTANBUL' but 'istanbul'.toLocaleUpperCase('TR') === 'İSTANBUL'. This bites hardest in CSS too — `text-transform: uppercase` on a Turkish string in a browser respects the element's lang attribute, so set lang="tr" on your carousel HTML root or your all-caps headlines will read wrong. Same class of bug applies to case-insensitive comparison and slug generation.

**CSS hyphens + Turkish hyphenation dictionary** — Direct consequence for your build: if you render Instagram/LinkedIn carousels by screenshotting HTML with Puppeteer/Playwright (Chromium), `hyphens: auto` with lang="tr" does NOTHING. Turkish words are long and agglutinative, so you WILL get ugly overflow or huge rag. Mitigations: (a) render with Firefox via Playwright if you want real hyphenation, (b) use a JS hyphenation library with Turkish patterns (Hyphenopoly / hyphen with TeX tr patterns) to inject soft hyphens (­) server-side, or (c) design layouts with generous measure and let Satori wrap on whole words only. Option (b) is the robust one.

**Chatterbox Multilingual v3 (Resemble AI)** — Repo includes Podonos MOS-style evaluation reports comparing Chatterbox Turbo against ElevenLabs Turbo v2.5, Cartesia Sonic 3 and VibeVoice 7B on preference/naturalness/expressiveness (specific win rates not stated in the README text I could read — verify the reports yourself). ### Öneriler

- ARCHITECT AROUND THE DIACRITIC DEFECT, NOT THE PROMPT. Install ceaksan/turkish-diacritics (MIT) as a mandatory PostToolUse hook on every Turkish text artefact, on BOTH the free and premium lanes, before anything enters the approval queue. The evidence is explicit that system-prompt instructions to preserve ç ğ ı ö ş ü decay past ~1500 words. It costs zero tokens because it runs outside the LLM loop, so it does not perturb your dual-lane cost model at all. Add a hard rule: no artefact reaches `status=pending_approval` without a passing diacritics check recorded on the record.
- NEVER LET AN IMAGE MODEL RENDER TURKISH TEXT. Make this a schema-level rule: image-generation steps emit text-free imagery only, and a separate compositing step lays down real text. Free lane and premium lane both use the SAME compositing step — Satori (MPL-2.0) → SVG → sharp.composite() with an explicit `fontfile` absolute path and `density` raised above the 72 DPI default. This single decision makes Turkish text quality INDEPENDENT of which image model you buy, which is exactly what a dual-lane cost model needs: the free lane and premium lane produce identically-correct typography and differ only in imagery quality. Ideogram's own docs admit accented Latin 'may have some difficulty being rendered correctly, if at all', and Google publishes no language list for Nano Banana Pro.
- BUILD A `tr-text` UTILITY MODULE AND BAN THE RAW PRIMITIVES. It must export: upper(s) → s.toLocaleUpperCase('tr'), lower(s) → s.toLocaleLowerCase('tr'), slug(s) with explicit ı→i / İ→i / ğ→g / ş→s / ö→o / ü→u / ç→c mapping, and foldForSearch(s) for diacritic-insensitive matching. Add an ESLint rule banning bare .toUpperCase()/.toLowerCase() in any file under the content pipeline. Set lang="tr" on the root of every HTML template so CSS text-transform:uppercase behaves. This is a 40-line module that prevents the most embarrassing possible Turkish bug: shipping a carousel that says ISTANBUL instead of İSTANBUL.
- SOLVE HYPHENATION IN JS, NOT CSS, BECAUSE YOU WILL RENDER IN CHROMIUM. Chrome has zero support for the Turkish hyphenation dictionary (Firefox/Safari only, 19.44% global). Turkish words are long and agglutinative, so Instagram/LinkedIn carousel layouts WILL break.
