## Özet

As of Aug 2026 the "free lane / premium lane with a pre-run estimate" problem is largely solved for TEXT and now, unusually, mostly solved for MEDIA too — but by two different stacks. For text, LiteLLM Proxy (self-hosted) remains the only OSS component that gives you per-request cost rows in your own Postgres, virtual keys, and stacked hard budgets (per key/user/team/model, multiple concurrent windows, soft-budget alerts, DB-backed enforcement, and an explicit "free models stay usable when budget is exhausted" behaviour). OpenRouter gives the richest routing knobs (order/only/ignore/sort=price/max_price/zdr/data_collection) plus a public pricing JSON and genuine $0 `:free` models — capped at 50 req/day (1000 with $10 credits). The surprise of 2026 is Vercel AI Gateway: one endpoint that covers language, embedding, reranking, IMAGE and VIDEO models, an unauthenticated `GET /v1/models` returning `pricing.image`, `pricing.video_duration_pricing[].cost_per_second` and `video_token_pricing`, zero markup, a real free tier on a model subset, and first-class budgets (team/project/API-key, daily/weekly/monthly/none, HTTP 402 `quota_for_entity_exceeded`, 50/75/100% email alerts, CLI + Quotas API). Paired with AI SDK 6's `experimental_generateVideo` (`doStart`/`doStatus`, JSON-serializable operation handle, signed webhooks, idempotency-key dedupe on the billable start call), that is effectively "LiteLLM for media" — the thing that did not exist a year ago. There is still no OSS equivalent, so a thin hand-rolled adapter interface over fal/Replicate/ComfyUI is still needed for models the gateway lacks. Pre-run estimation is a pricing-catalog problem, not an SDK problem: snapshot LiteLLM's `model_prices_and_context_window.json` + the gateway `/v1/models` JSON into a git-committed file, tokenize with gpt-tokenizer, and price media by unit count. Langfuse (MIT, ClickHouse-owned since Jan 2026) closes the loop: it accepts arbitrary usage types and directly ingested `cost_details`, so image/video steps land in the same cost-per-run trace as tokens.

**LiteLLM Proxy (self-hosted)** — Licence: open source core + 'LiteLLM Commercial License' for enterprise bits — read LICENSE before assuming MIT. Its budget model maps 1:1 onto your 'per-project budget' requirement: one virtual key per client/project.

**LiteLLM model_prices_and_context_window.json** — Model count reported as ~350-400 by the fetch summary but the real file is far larger — treat the count as UNVERIFIED. Snapshot it nightly and COMMIT the snapshot so an estimate shown to you is reproducible and git-backed.

**OpenRouter** — Docs explicitly say free models have low limits and are 'usually not suitable for production'. Whether prompts on :free endpoints are trained on is NOT answered by the privacy docs — treat the free lane as non-confidential-only. That matters directly for prospect-specific sales decks.

**Vercel AI Gateway** — You pay payment-processing fees. Its free tier gives you a second free lane alongside OpenRouter. Turkey card acceptance UNVERIFIED. Note the deliberate coupling: pricing catalog, budgets, and execution are one system, which is exactly what your estimator needs.

**Vercel AI Gateway Budgets** — CRITICAL CAVEAT documented by Vercel: 'A budget is a soft cap, not a hard limit' — the check runs at request start, so the crossing request completes and spend can end slightly over. Budget changes take tens of seconds to ~5 minutes to apply. BYOK spend is NOT counted in budgets at all. So you still need your own local ledger for a true hard stop.

**Vercel AI SDK v6 (ai) — provider registry + generateImage + experimental_generateVideo** — Two details worth copying into your own adapters: (1) the start request carries a stable idempotency-key because 'starting a generation costs money' and gateway retries must not bill twice; (2) doStart/doStatus separation means the process that starts a 6-minute video need not be the one that reads it. Node's Undici 5-minute fetch timeout will kill long single-request video calls — use poll or a custom Agent with 15-min headersTimeout/bodyTimeout. generateImage does NOT return usage/cost, so you must attribute image cost yourself from the pricing catalog.

**fal.ai** — docs.fal.ai returned HTTP 429 on every attempt during this research, so the exact queue API surface (queue.fal.run submit/status/result, fal_webhook parameter, cancel, signature verification) is UNVERIFIED here — confirm against docs.fal.ai/model-apis/queue before coding the adapter. Pricing above IS verified from the live pricing page. Note fal video is priced PER SECOND, so your estimator must multiply by requested duration.

**Replicate** — Per-second GPU billing makes PRE-run estimation genuinely hard: cold starts and variable inference time mean you can only give a range. Estimate as [p50_seconds, p90_seconds] x hardware rate and show a range in the UI, never a single number. Prefer per-output-priced official models when you need a firm quote.

**ComfyUI** — LICENCE WARNING: ComfyUI is GPL-3.0. Calling it over HTTP as a separate process is fine; vendoring its code into your Next.js command center is not. Bigger risk is the model weights, not ComfyUI: for commercial Upcytech ads you must pick commercially-licensed checkpoints (FLUX schnell Apache-2.0 rather than FLUX dev).

**Google Gemini API (Gemini / Nano Banana / Veo)** — DECISIVE for your dual-lane policy: the pricing page states free-tier content IS 'used to improve our products' while paid-tier content is NOT. Company-specific sales presentations naming a real prospect must therefore be hard-blocked from the free lane. Encode this as a `confidential: true` flag on the pipeline that disables free-lane selection in the UI.

**Together AI** — Per-video flat pricing (not per-second) makes it the easiest video source to quote exactly in a pre-run estimate.

**Segmind** — Credit systems that reset monthly are hostile to your usage shape (a few big campaign bursts). Prefer prepaid balances that don't expire (fal, Replicate, Vercel credits).

**AI/ML API (aimlapi.com)** — Aggregators of aggregators add a second markup layer and a second point of failure. If Vercel AI Gateway already carries the model, prefer it.

**Eden AI** — Whether image/video GENERATION providers are in the 500+ catalog could not be confirmed from the pricing page. The 5.5% fee is transparent and predictable, which is more than most aggregators offer.

**Freepik / Magnific API** — The asset LICENCE question is the blocker, not the price: for Upcytech ad creative you need explicit commercial-use rights on generated output. Revisit once docs.magnific.com stabilises.

**Helicone** — Fully Apache-2.0 self-host is a genuine advantage over Langfuse's MIT-except-/ee split. But its cost model is token-centric; you'd be fighting it to log a 6-minute video render's cost.

**Portkey AI Gateway (OSS)** — CONFLICTING SIGNALS: portkey.ai docs state Portkey 'has transitioned to PRISMA AIRS AI Gateway under Palo Alto Networks', while the GitHub README shows no such notice and ongoing commits. Treat the long-term maintenance of the OSS repo as UNVERIFIED. For a solo operator, an acquisition-in-progress dependency is a bad bet versus LiteLLM.

**Cloudflare AI Gateway** — Its response caching at the edge is a genuinely different cost lever from prompt caching: identical requests never reach the provider at all. Worth a second look specifically for the deterministic, repeated steps in your pipelines (e.g. the same brand-system system prompt).

**Requesty** — Operational status in 2026 could not be independently confirmed. For a solo operator, fewer paid intermediaries is better; a 5% tax on every token to duplicate LiteLLM's budget feature is poor value.

**Martian (withmartian)** — Classic stale-training-data trap: the router product that appears in older comparisons is no longer the company's public offering.

**aisuite (andrewyng/aisuite)** — Useful only as prior art for the 'provider:model' addressing convention, which AI SDK's registry already implements better for TS.

**any-llm (Mozilla AI)** — The fact that Mozilla AI had to spin budgets out into a separate project (otari) is itself evidence that budget enforcement is a gateway concern, not an SDK concern. Design accordingly: put budgets at your egress proxy, not in your adapter code.

**Langfuse** — Langfuse became part of ClickHouse in January 2026 — good for durability, but watch for the MIT core's scope narrowing over time. Self-hosting keeps your prospect data (client names in sales decks) on your machine, which the free-lane training-data risk makes non-optional.

**OpenMeter** — Its real use case is BILLING YOUR CUSTOMERS by usage, not tracking your own spend. Revisit only if Upcytech ships a usage-metered SaaS product; for internal cost-per-run, Langfuse + a Postgres ledger table is the right size.

**OpenTelemetry GenAI semantic conventions** — The Schema URL section reads 'TODO' and the attribute set is still churning; per-attribute stability, and whether cost or image/video generation operations are covered at all, is UNVERIFIED. Practical stance: emit gen_ai.* where it exists, put everything else in your own namespace, and let Langfuse's gen_ai.usage.cost mapping carry the money.

**Anthropic prompt caching** — Perfect structural fit: your brand system, product knowledge and business strategy are a large, stable prefix reused across every Instagram/LinkedIn/deck generation. Put the whole knowledge base in the cached prefix with a 1h TTL during a working session and only the prospect-specific tail outside it. Cache is invalidated by changes to tools, system prompt, tool_choice, images, thinking config, or output_config.effort — so freeze those per session. Your estimator MUST model three token classes, not two, or it will over-quote by ~10x on the cached portion.

**tokencost (AgentOps-AI)** — Its design confirms the right decomposition: tokenizer + price table + a function per direction. That's ~150 lines to reimplement in TypeScript over gpt-tokenizer and the LiteLLM price JSON, with no Python process in your stack.

**gpt-tokenizer** — Caveat: it is an OpenAI BPE tokenizer. For Claude, token counts differ — use Anthropic's count_tokens endpoint for exact figures, or apply a calibration factor and widen your estimate range. Never present a Claude estimate derived from o200k_base as exact.

**GPTCache** — More importantly, semantic caching is the WRONG tool for your workload. Your value is in fresh, differentiated creative per prospect — serving a near-match cached LinkedIn post is a quality bug, not a saving. Use content-hash (exact) caching of MEDIA instead, where re-rendering the identical prompt+seed+model is pure waste.

**RedisVL SemanticCache** — Where it DOES pay off in your suite: the deterministic non-creative steps — brief classification, tone checks, Turkish grammar QA, prospect-research summarisation. Cache those at threshold 0.05-0.1; never cache the generation step. Note the docs page redis.io/docs/latest/develop/ai/langcache/ 404'd, so a managed Redis LangCache service is UNVERIFIED.

**Inngest** — For a LOCAL command center the self-hosted path matters more than the cloud tiers; confirm exactly which features the self-hosted engine includes before committing (UNVERIFIED). Its step model maps cleanly onto your pipeline steps, giving per-step retry and per-step cost attribution for free.

**Trigger.dev** — The 'no charge while waiting' property is the decisive difference from Inngest for your workload: a pipeline that starts a video job and sleeps 6 minutes costs you the two short steps, not the wall clock. Pair with AI SDK's poll.delay hook — the docs explicitly suggest passing a durable workflow's sleep function so no live timer is held.

- THE ADAPTER INTERFACE you must hand-roll (only for providers the AI SDK lacks — fal-only models, ComfyUI, Replicate custom models). Five methods, modelled on what AI SDK's video provider proved necessary:

interface MediaAdapter<TInput, TAsset> {
  id: string;                       // 'fal:kling-2.5-turbo-pro'
  kind: 'image' | 'video' | 'tts' | 'asr';
  lane: 'free' | 'premium';
  estimate(input: TInput): CostEstimate;                 // pure, synchronous, no network
  start(input: TInput, ctx: { idempotencyKey: string; webhookUrl?: string }): Promise<Operation>;
  status(op: Operation): Promise<{ status: 'pending'|'completed'|'error'; assets?: TAsset[]; error?: string }>;
  cancel(op: Operation): Promise<void>;
  actualCost(result: unknown): number | null;            // null => fall back to estimate
}

NON-NEGOTIABLE PROPERTIES, each learned from a primary source: `Operation` MUST be an opaque JSON-serializable handle (Vercel: 'persist it as-is rather than parsing it') so the process that starts a 6-minute render is not the process that reads it. `start` MUST accept an idempotencyKey because, in Vercel's words, 'starting a generation costs money' — retries must not bill twice. `estimate` MUST be pure and network-free so the UI can recompute it on every keystroke. `actualCost` returns null rather than throwing, because generateImage returns no usage and per-second GPU providers (Replicate) cannot be known in advance.
- COST ESTIMATION BEFORE THE RUN — build a `pricing.snapshot.json` committed to git, refreshed by a nightly job from exactly two sources: LiteLLM's model_prices_and_context_window.json (fields input_cost_per_token, output_cost_per_token, cache_read_input_token_cost, cache_creation_input_token_cost, output_cost_per_image, input_cost_per_pixel, output_cost_per_video_per_second, input_cost_per_audio_per_second) and the unauthenticated GET https://ai-gateway.vercel.sh/v1/models (fields pricing.input, pricing.output, pricing.image, pricing.video_duration_pricing[].cost_per_second keyed by resolution, pricing.video_token_pricing.tiers, pricing.cachedInputTokens, pricing.cacheCreationInputTokens, pricing.inputTiers). Committing the snapshot is what makes a quoted estimate reproducible and auditable months later — which matters when the estimate was shown to justify spend on a specific client's deck.

Estimate math per step:
- TEXT: tokens_in (gpt-tokenizer, o200k_base) split into THREE buckets — cached_read, cache_write, fresh_input — then + estimated tokens_out. Estimating output is the weak point: keep a rolling median of actual output tokens per step_id from your own run history and use [p50, p90] as the range. Never quote a single number for text.
- IMAGE: n x price_per_image, or n x megapixels x price_per_megapixel (fal Qwen bills per MP). Exact and quotable.
- VIDEO: duration_seconds x cost_per_second AT THE REQUESTED RESOLUTION (Seedance v1.0 Pro is $0.0243/s at 480p and higher above), or a flat per-video price (Together), or token-based (Seedance 2.0 video_token_pricing). Three different shapes — your estimator needs three branches.
- PER-SECOND GPU (Replicate/ComfyUI cloud): unquotable in advance. Model as [p50_seconds, p90_seconds] x hardware_rate from your own history and mark the line item confidence:'low'.

Output type: CostEstimate { minUsd, maxUsd, currency:'USD', lines: [{ stepId, lane, provider, model, unit, quantity, unitPrice, subtotalMin, subtotalMax, confidence:'exact'|'ranged'|'low' }], snapshotVersion: string }.

- BUDGET GUARDRAILS — three layers, because none alone is sufficient. (a) PROVIDER-SIDE: one Vercel AI Gateway API key per project/client with its own budget via `vercel ai-gateway api-keys create --name upcytech-prospect-x --budget 25 --refresh-period monthly`, plus a team budget and a project-default budget as a catch-all; alerts at 50/75/100%. (b) EGRESS-SIDE: LiteLLM virtual keys with model_max_budget and stacked windows (budget_limits: [{24h, $5}, {30d, $60}]) — LiteLLM's DB-backed enforcement is stricter than the gateway's. (c) LOCAL-SIDE: your own pre-flight check that refuses to start a run whose ESTIMATE exceeds pipeline.budget.max_usd_per_run.

WHY ALL THREE: Vercel's own docs state 'A budget is a soft cap, not a hard limit... the request that crosses the limit still completes and total spend can end up slightly over', changes take up to ~5 minutes to apply, and BYOK spend is not counted in budgets at all. LiteLLM is the only layer that gives you a genuinely hard, locally-owned cap. Handle HTTP 402 quota_for_entity_exceeded as a first-class UI state ('Bütçe aşıldı'), not a generic error.
- CACHING STRATEGY, ranked by actual payoff for your workload:
1. ANTHROPIC PROMPT CACHING (biggest lever, by far). Your brand system + product knowledge + business strategy is a large stable prefix reused by every Instagram, LinkedIn and deck pipeline. Cache reads cost 0.1x base input — a 90% cut on the prefix. Use ttl:'1h' (2x write cost, amortised within one working session) rather than the 5m default. Freeze tools, system prompt, tool_choice, images and thinking config for the session, since any change invalidates the cache. Respect the per-model minimum (512 tokens for Opus 5, up to 4,096 for Haiku 4.5) — below it nothing caches and NO ERROR IS RETURNED, so verify by asserting cache_read_input_tokens > 0 in your traces.
2. CONTENT-HASH CACHING OF GENERATED MEDIA (second biggest, and entirely yours to build). Key = sha256(provider + model + normalised_params + prompt + seed + input_asset_hashes). Store in a local CAS directory with a Postgres index; a hit returns the existing file at zero cost. Re-rendering an identical image or video is pure waste and is common when iterating on a deck's copy while the visuals are unchanged.
3. IDEMPOTENCY KEYS on every billable start call (see adapter interface) — this prevents duplicate BILLING, which is a different failure from duplicate work.
4. ASSET REUSE LIBRARY — a queryable index of previously generated assets with their prompts and costs, so 'reuse' is a first-class option in the UI alongside 'free lane' and 'premium lane'. The cheapest generation is the one you don't run.
5. SEMANTIC CACHING: REJECT for creative steps. Serving a near-match LinkedIn post is a quality defect. Apply RedisVL SemanticCache (threshold 0.05-0.1) only to deterministic non-creative steps — brief classification, Turkish grammar QA, prospect-research summarisation.
- QUEUE / RETRY ACROSS 5-SECOND AND 6-MINUTE STEPS — the unifying pattern is: every long step is (start -> persist opaque operation -> resume on webhook, fall back to polling). Concretely: a Trigger.dev task calls adapter.start() with an idempotencyKey and a webhookUrl pointing at a local tunnel/route; it then waits on the webhook with a polling fallback. Vercel AI Gateway signs deliveries with x-ai-gateway-signature: t=<unix seconds>,v1=<HMAC-SHA256 of "<t>.<raw body>"> — verify against the RAW bytes and reject timestamps older than 5 minutes; deduplicate on x-ai-gateway-idempotency-key (<jobId>-<status>); it expects 2xx within 10 seconds and does not follow redirects. Replicate uses webhook + webhook_events_filter: ['completed'] and offers `Prefer: wait[=n]` (default 60s) for the short-latency case. Two hard-won details: (1) webhook payloads are deliberately thin — Vercel's carries jobId/status/timestamps and NEVER the video URL, so the webhook is only a signal to call status(); (2) provider-hosted result URLs EXPIRE (result.expiresAt), so download and store every asset in your local CAS immediately, before the pipeline continues. In Node, the default Undici fetch enforces a 5-minute timeout that will kill a long single-request video call — either use the async job flow or construct an Agent with 15-minute headersTimeout/bodyTimeout.
- OBSERVABILITY OF COST PER RUN — self-host Langfuse (MIT except /ee) and make the pipeline run the trace. One trace per pipeline run, one observation per step. For text steps let Langfuse infer cost from tokens; for image/video steps INGEST the cost directly via cost_details, which Langfuse prioritises over inference, using arbitrary usage-type keys ('images','video_seconds','gpu_seconds') — its docs state usage types 'can be arbitrary strings' and act as mutually exclusive buckets. Register your media models as custom models (Project Settings > Models or the Models API) with regex name matching and per-usage-type pricing so the UI groups them properly. Feed traces over OTLP HTTP to /api/public/otel with Basic Auth (base64 pk:sk) and header x-langfuse-ingestion-version: 4; emit gen_ai.request.model, gen_ai.usage.* and gen_ai.usage.cost, which Langfuse maps natively. Self-hosting is not optional here — prospect names and deal context in your traces must not leave your machine. Add one non-Langfuse thing: your own `runs` and `run_steps` Postgres tables storing estimate_min, estimate_max, actual_cost and pricing_snapshot_version per step, so you can compute estimate-vs-actual drift and tighten the estimator over time.
- UI: HOW THE ESTIMATE IS SHOWN. A pre-run drawer with one row per step: step name (Turkish), a FREE/PREMIUM segmented toggle, provider+model, the quantity and unit ('20 sn video', '8 görsel', '~51k token'), and the cost as a RANGE with a confidence dot (green=exact per-unit media pricing, amber=ranged token estimate, red=per-second GPU). Rules: (a) always show a range, never a false-precision single number — media is exact, text is not; (b) a master FREE/PREMIUM toggle sets all steps at once, with per-step overrides persisting, so the common case is one click and the mixed case (premium copy + free images) stays possible; (c) the Run button is disabled with a Turkish explanation when max estimate exceeds pipeline.budget.max_usd_per_run; (d) for confidential:true pipelines the free toggles are visibly disabled with a reason, not silently absent; (e) after the run, show estimate vs actual side by side on the same rows — this is what makes the next estimate trustworthy; (f) show prices in USD with a TRY conversion beside them, and label the TRY figure as indicative, since provider billing is USD-denominated.
