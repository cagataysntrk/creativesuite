## Özet

The good news: the "brand that changes over time" problem is already solved as a standard, just not marketed that way. The W3C DTCG published two Final Community Group Reports on 28 Oct 2025 that are explicitly marked stable and implementable: the Format Module (reserved props $value, $type, $description, $extensions, $deprecated, $extends, $ref, $root) and the Resolver Module (sets + modifiers + contexts + ordered resolution). Multi-theme, multi-brand and multi-ERA are the same problem, and the Resolver models all three as orthogonal modifiers, avoiding combinatorial file explosion. $extends gives parent-brand → child-brand (Upcytech → dima) inheritance; $deprecated (true | "explanation" | false, inheritable from groups) gives per-token retirement with a reason. A newer preview draft dated 30 Jul 2026 exists but says do not implement — build against 2025.10.

Production practice confirms the model. @atlaskit/tokens 16.7.0 (Apache-2.0) stamps every token with attributes {group, state, introduced: "1.6.0", description}, ships a codegen'd replacement-mapping whose own header documents the five-step rename ritual (mark old state deprecated → add replacement → add new token → rebuild → ESLint/codemods auto-migrate usages), and ships "Legacy light", "Light" and "Light future" themes in one package — three brand eras alive simultaneously. @primer/primitives 11.10.0 (MIT) implements the DTCG $deprecated flag over Style Dictionary and emits dist/deprecated.json as an old→new name map. Adobe ships two design languages as two packages side by side (@adobe/react-spectrum 3.47.3 and @react-spectrum/s2 1.6.0). GOV.UK Frontend publishes the deprecation policy in the repo: deprecate in a minor, remove in the next major, never deprecate in a patch, with a tracked removal issue on the major milestone.

For regeneration, no product does "re-run brand discovery and diff it". You assemble it from four verified primitives: SignedSource-style @generated signatures to detect human edits to machine files; git merge-file --diff3 for 3-way merge; jd/difftastic for structured semantic diff; Directus-style snapshot → diff → apply with a hash guard as the plan/apply contract. The missing piece — a sticky accept/reject decision ledger — you must build.

### Öneriler

- MODEL AN ERA AS A NEW NAMESPACE AT v1.0.0, NOT A MAJOR BUMP. Follow Adobe: @adobe/react-spectrum 3.47.3 and @react-spectrum/s2 1.6.0 ship side by side. Layout: brand/eras/<era-slug>/ where era-slug is date-prefixed and human-readable (2024-recycling-software, 2026-manufacturing-ai). Each era directory owns era.yaml (id, ulid, label, status ∈ candidate|active|sunset|archived, valid_from, valid_to, supersedes, generator{model, prompt_hash, input_hashes, run_id}), tokens/, messaging/, personas/, and evidence/. A repositioning creates a directory; it never rewrites one.
- USE TWO VERSION IDENTIFIERS, NOT ONE. (1) era_id — an opaque, immutable identity, never reused, never renumbered. (2) kit_version — semver WITHIN an era, following the GOV.UK rule set: MAJOR = a declared-public-API name is renamed or removed (token name, message key, claim id, persona id, channel id); MINOR = additions and deprecations; PATCH = value/wording change behind a stable name. Never deprecate in a patch. Declare that public API explicitly in brand/POLICY.md the way GOV.UK declares theirs, otherwise semver is meaningless for subjective brand changes.
- STAMP EVERY ATOM WITH ITS PROVENANCE, COPYING @atlaskit/tokens EXACTLY. Every token, message, claim and persona field carries attributes {state: active|experimental|deprecated|removed, introduced: '<kit_version>', description, replacement?: '<new.key>'}. Then generate — never hand-write — a replacement-map.json per era transition, exactly as Atlassian's replacement-mapping.js and Primer's dist/deprecated.json do. That generated map is what lets a codemod mechanically upgrade a 2024 deck to 2026 language, and what lets the UI say 'this asset uses 3 retired claims'.
- MAKE THE RESOLVER, NOT THE FOLDER, THE SWITCH. Adopt the DTCG Resolver Module 2025.10: declare modifiers era, brand, channel, mode, each with a contexts array, and a resolution order where later sets override earlier. Adding a brand era, a sub-brand (dima), a new channel or a new candidate direction becomes appending one object to a JSON array — no code change, which is precisely constraint (a). Use DTCG $extends for parent-brand → child-brand token inheritance so dima's file contains ONLY its overrides.
- SPLIT EVERY ERA DIRECTORY INTO FOUR ZONES WITH DIFFERENT OWNERS: inputs/ (frozen, content-addressed snapshots of the sources the discovery ran on — interviews, site scrapes, customer calls; immutable), generated/ (machine-owned; every file carries a SignedSource '@generated <<SignedSource::hash>>' header), overrides/ (human-owned; the regenerator NEVER writes here and always layers it last), and resolved/ (build output, gitignored or committed as a lockfile). The generated/overrides split plus the signature is the entire answer to the generated-vs-hand-edited problem — the founder's edits are never 'in the way of' a regeneration because they live in a different zone.
- NEVER REGENERATE IN PLACE. Every discovery run happens on a git worktree at branch regen/<era>/<run-id> and ends as a draft PR, TinaCMS-style — the founder approves in the command center and never sees git. Keep a pristine copy of the previous run's generated output under .brand/base/<era>/ so you can always run `git merge-file --diff3 -L yours -L last-run -L regenerated` when a file must genuinely be merged rather than replaced. merge-file's exit code is the conflict count, so the pipeline can gate on it.
- IMPLEMENT PLAN/APPLY WITH A HASH GUARD, COPYING DIRECTUS. `discovery plan` emits plan.json = {base_hash, ops[]} where each op is {path, json_pointer, kind: add|change|deprecate|remove, before, after, confidence, rationale, source_refs}. `discovery apply --plan plan.json` recomputes base_hash and REFUSES if it changed (with an explicit --force). Offer two modes exactly as Directus does: merge (additive only, never deletes — the safe monthly refresh) and mirror (full regeneration including deletions — the 'do it all again from scratch' button). Generate ops with jd so array reordering and volatile fields (generated_at, model, token counts) are excluded from the diff.
- BUILD A STICKY DECISION LEDGER — THIS IS THE PIECE NOTHING OFF-THE-SHELF GIVES YOU. Every accept/reject in the review UI appends to decisions.jsonl: {json_pointer, from_hash, to_hash, verdict: accept|reject|pin, reason, era, at}. On the NEXT regeneration, any op whose (pointer, to_hash) was previously rejected is pre-collapsed as 'you rejected this before'; any pointer marked `pin` is excluded from the plan entirely (the .openapi-generator-ignore idea, per-field instead of per-file). Without this, the fourth re-run makes him re-litigate the same 200 decisions and he will abandon the system.
- MAKE THE DIFF UNIT ONE CLAIM PER FILE. Prose merges badly; line-level conflicts in a 600-word positioning statement are unreviewable. Store messaging as many small files (messaging/claims/efficiency-gain.md with front-matter id, state, introduced, evidence refs) rather than one manifesto. Then accept/reject is file-level and whole-object, git's `s`(split) verb is never needed, and the UI can show a clean side-by-side. Assemble the manifesto at build time from the claim files.
- PUBLISHED ASSETS ARE IMMUTABLE AND SELF-DESCRIBING. At publish time write front-matter {era_id, kit_version, resolver_context {era, brand, channel, mode}, source_plan_run_id, content_hash, published_at, channel_url} and append the same record to ledger/published.jsonl. Never rewrite a published asset when an era retires. `era retire <id>` sets status: sunset and valid_to, and does exactly three things: marks the era, regenerates the lineage/replacement map, and emits content-audit.md listing every still-live published asset from the retired era, classified update | archive | leave-as-history. Canonical surfaces (website, master deck, one-pager) get a hard cutover date; social archives simply stay tagged to their era.
- RUN CANDIDATE BRAND DIRECTIONS AS PARALLEL CANDIDATE ERAS WITH A FIXED PROBE SET. Several eras may sit at status: candidate simultaneously (Sanity Content Releases' 'Undecided' type — publish actions deliberately hidden). To compare them, define probes/ once: e.g. 5 Instagram posts, 3 LinkedIn posts, 1 deck for a named prospect archetype, 1 ad set. Render the identical probe set under each candidate context and diff/score them side by side. Golden-file bake-off, deterministic, no A/B infrastructure needed. Promotion is a single field flip candidate → active plus valid_from.
- PIN THE GENERATOR OR YOUR DIFFS WILL BE NOISE. LLM nondeterminism will make every re-run diff 100% of the corpus, which destroys the entire review workflow. era.yaml must record generator {provider, model_id, temperature, seed, prompt_template_hash, retrieval_snapshot_id, input_file_hashes}. Skip regeneration for any section whose input hashes AND prompt hash are unchanged (idempotent no-op, the Hygen skip_if lesson). Only genuinely changed inputs produce ops. This one rule is the difference between a reviewable 12-op plan and an unreviewable 900-op plan.
- BUILD AGAINST 2025.10, NOT THE 2026 DRAFT. The Format and Resolver modules dated 28 Oct 2025 are Final Community Group Reports marked stable; the preview draft dated 30 July 2026 says in its own header 'Do not attempt to implement this version'. Record the spec edition in era.yaml so a future superseding spec is itself an era-scoped decision.
- WRITE brand/POLICY.md NOW, BEFORE THE FIRST ERA. Copy GOV.UK's managing-change doc almost verbatim: what the public API is, legitimate vs illegitimate reasons for a breaking change, deprecate-in-minor / remove-in-next-major / never-in-patch, always explain a deprecation in plain language rather than assuming the word is understood, emit suppressible warnings, and open a tracked removal task attached to the next major. A solo founder needs this MORE than a team does, because there is no colleague to stop him renaming things on a hunch.


### Riskler

- OVER-ENGINEERING IS THE PRIMARY RISK. Everything above is assemblable by one person, but the full stack (resolver + signatures + 3-way merge + plan/apply + decision ledger + probe-set bake-off) is a multi-week build with ongoing maintenance. Minimum viable version that still satisfies all four constraints: era directories + DTCG tokens with $deprecated + branch-per-regeneration + jd-based plan.json + accept/reject UI + published-asset front-matter stamps. Add SignedSource, resolver modifiers and the decision ledger only when the first re-run actually hurts.
- THE DTCG RESOLVER MODULE IS YOUNG. Published 28 Oct 2025; I could not verify a single shipped OSS implementation. Terrazzo's own docs still say resolver support is 'coming in 2.0' even though its CLI is at 2.7.1 — that contradiction is unresolved. If you adopt the resolver, be prepared to write ~200 lines of resolution logic yourself. The FORMAT module is safe (two major design systems verified using $deprecated in production); the RESOLVER is the bet.
- DTCG COVERS TOKENS ONLY — NOT MESSAGING, PERSONAS, CLAIMS OR CHANNELS. Roughly 80% of the brand DNA in this suite is prose and strategy, for which there is no standard and no $deprecated equivalent. You must define that metadata schema yourself (mirroring the Atlassian attributes shape is the cheapest defensible choice), and it will be the part that rots if not governed.
- SEMVER ON SUBJECTIVE BRAND CHANGES IS GENUINELY CONTESTED. GOV.UK's own doc concedes 'a UI library often has subjective changes such as visual spacing changes'. Is 'we now say precision-engineered instead of high-precision' a patch or a minor? Without a declared public API the answer is arbitrary and the version numbers stop carrying information. Mitigation is the declared-API rule; residual ambiguity remains.
- LLM NONDETERMINISM CAN KILL THE DIFF REVIEW OUTRIGHT. If the discovery engine re-words unchanged material on every run, the plan is 100% noise and the founder will click accept-all, which is functionally identical to having no review at all. Input-hash-gated skipping and pinned model/prompt/seed are mandatory, not optional — and even then, expect to invest real effort in prompt stability and in jd allow/deny-lists for volatile fields.
- PROSE MERGE CONFLICTS ARE UNPLEASANT AND git merge-file WILL PRODUCE THEM. Conflict markers inside a paragraph of Turkish or English brand copy are hostile to review. Mitigated by one-claim-per-file granularity, but any file that legitimately mixes generated and hand-written prose will eventually conflict. Prefer strict zone separation (generated/ vs overrides/) over merging wherever possible.
- GITHUB API AND WEB SEARCH LIMITS CONSTRAINED THIS SURVEY. The session's WebSearch budget (200/200) was exhausted before this task began, and the unauthenticated GitHub API rate-limited mid-research. Findings were recovered via direct primary-source fetches (specs, npm/jsDelivr artifacts, raw GitHub markdown) plus a DuckDuckGo HTML fallback, but the survey is NOT a complete 2026 market scan — a purpose-built 'brand era' product could exist and be absent here.
- STAR COUNTS AND OPEN-ISSUE COUNTS ARE WEAK MAINTENANCE SIGNALS AND I COULD NOT GET LAST-COMMIT DATES for Hygen, Plop and jscodeshift (GitHub API rate limit). All three are widely used and none look abandoned, but confirm last-release dates before depending on any of them. difftastic (0.70.0, updated 2026-08-07) and style-dictionary (5.5.1, published ~2026-08-07) are the two confirmed-fresh dependencies.
- LICENCE TRAPS: Unleash server is AGPL-3.0-or-later (matters the moment any of this is exposed as a service); Directus's current licence terms above a revenue threshold were NOT verified; TinaCMS's OSS licence was NOT verified and its licensing has changed historically. Verify before embedding any of them rather than merely copying their patterns.
- AN IMMUTABLE PUBLISHED LEDGER CREATES A COMPLIANCE SURFACE. Permanently retaining every asset with prospect-personalised deck content and persona data means the ledger becomes a personal-data store under KVKK/GDPR. Design the ledger so asset METADATA (era, hashes, timestamps) is immutable but prospect-identifying PAYLOADS are separable and deletable, or era attribution will collide with erasure requests.
