## Özet

The session's WebSearch budget was already exhausted before I started, so every finding below comes from direct WebFetch of primary docs/repos (no search-result summaries). Where a fetch 404'd or the page didn't cover the question, I marked it UNVERIFIED rather than filling from memory.

Conclusion: do not build a plugin API. Build three git-backed data registries — pipelines, providers, channels — each described by one JSON Schema generated from one Zod source, and a deliberately tiny fixed set of ~8 executable verbs. Everything the founder adds is a YAML file; a developer is only needed to add a verb, which should happen ~twice a year.

For the pipeline format, the evidence favours the Kestra/GitHub-Actions shape (flat ordered `steps:` with `id` + `uses` + `with` + `needs`, plus a JSON Schema `inputs:` block) over node+edge canvas JSON (n8n, Langflow, ComfyUI, Flowise). Canvas formats carry coordinates, `typeVersion` and edge ids that exist for a renderer, not an author; ComfyUI's own executable form collapses to a `{id: {class_type, inputs}}` map, which proves the graph chrome is incidental. The Actions vocabulary is the single most agent-authorable option because it is the densest workflow dialect in any LLM's training data. Windmill's OpenFlow supplies the one thing Actions lacks and you will need: `rawscript` as an inline escape hatch, plus `mock:` per module for dry-runs.

For providers, config-as-provider is already proven: Vercel AI SDK's `createOpenAICompatible({name, baseURL, apiKey, headers, queryParams})` builds a working provider from pure data, `createProviderRegistry` now resolves `languageModel/imageModel/videoModel` from `provider:model` strings, LiteLLM carries cost as data (`input_cost_per_token`, `input_cost_per_second`, `input_cost_per_video_per_second`), OpenRouter publishes capability metadata (`architecture.input_modalities`, `supported_parameters`, `pricing.*`), and fal serves a live OpenAPI 3.0.4 document per model endpoint — so provider descriptors can be *imported*, not typed. Capability routing (filter by declared tags/constraints → estimate cost from a formula → score → ordered fallback) has partial prior art in OpenRouter provider preferences, LiteLLM tag routing and Helicone's gateway, but no OSS system solves the media case; that router is ~300 lines you own.

**Kestra flow YAML** — `pluginDefaults` is the pattern to steal for per-era defaults (e.g. all image steps in era X get the same style_ref). Auto-revisioning is right but lives in Kestra's DB; in a git-backed suite git IS the revision store. UNVERIFIED: I could not confirm a `flow validate` CLI command or a POST /flows/validate endpoint — both doc URLs 404'd.

**Windmill OpenFlow** — The Apache-2.0 licensing of the OpenFlow spec itself means you can legally implement it. Windmill also stores flows on disk as `<name>.flow/flow.yaml` + inline scripts, synced with `wmill sync pull/push` and `wmill dev` live-reload — direct proof that a git-of-truth + local-command-center architecture works. `input_transforms` as restricted JS is exactly the templating problem you'll hit; they solved it with a constrained expression evaluator, not full JS.

**GitHub Actions workflow syntax** — UNVERIFIED (not fetched this session — I ran out of search budget and prioritised less-known sources). Known limits to design around: no true dynamic loops without matrix gymnastics, and expressions are stringly-typed. Fix both by making `foreach:` first-class and by validating every `{{ }}` reference against declared inputs/step-outputs at lint time.

**n8n workflow JSON** — Licence verified verbatim: 'You may use or modify the software only for your own internal business purposes or for non-commercial or personal use.' Internal use at Upcytech is fine; embedding or reselling it inside a productised creative suite is not. Format-wise, `typeVersion` + `position` + edge maps are renderer artefacts that make hand/agent authoring error-prone. UNVERIFIED: exact export field list (docs URL 404'd).

**Dagster Components (`dg`)** — UNVERIFIED: the docs page I fetched did not confirm the exact `defs.yaml` shape, the `type:` key, or whether each component type publishes a JSON Schema. Treat my design's 'scaffold + validate' CLI as inspired-by, not ported-from.

**Temporal workflow versioning** — The takeaway for a data-defined pipeline suite: never let a run resolve against the live YAML. Freeze the fully-resolved plan at trigger time and execute the frozen artefact. That sidesteps the entire determinism/patching problem class rather than solving it.

**Trigger.dev versioning & run pinning** — Copy their split explicitly into your CLI/UI as two distinct buttons: `rerun` = execute the frozen plan (reproducible), `replay` = same inputs against today's definition (shows drift). Their one gap — no way to run an old version directly — you can close for free, because your frozen plan IS the old version.

**Agent Skills open specification (agentskills.io)** — Strategically important for requirement (d): if the founder ever drops Claude Code, the pipeline-authoring skills port unchanged to whatever replaces it. Note the spec's frontmatter set is deliberately smaller than Claude Code's — a portable skill should stay inside the spec's six fields and put anything extra under `metadata`.

**Claude Skills in Claude Code (superset frontmatter)** — The three that matter: `disable-model-invocation: true` on every side-effecting skill (publish, deploy, spend) so Claude cannot fire them on its own; `user-invocable: false` for background knowledge; and `allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/validate.sh *)` which pre-approves exactly the validator and nothing else — the variable is substituted in BOTH the body and the Bash rule, so the command matches and runs prompt-free. Also: skill content persists in context for the rest of the session but the `allowed-tools` grant clears on your next message, and Claude Code does not re-read the file on later turns.

**Claude Code subagents** — `isolation: worktree` is the underrated field: an agent that rewrites registry YAML can be forced to do it in a throwaway git worktree, so the founder reviews a real diff and nothing touches the working tree until he merges. `memory: project` at `.claude/agent-memory/<name>/` gives the authoring agent cross-session learning that is itself git-visible and therefore governable (requirement c). Note `/agents` no longer opens a creation wizard as of v2.1.198 — you write the files.

**Claude Code plugin manifest & conventions** — The single most transferable design decision here: convention-first, manifest-only-to-override. A solo maintainer should never require a manifest to add a thing. Also copy the ADD-vs-REPLACE distinction (extending defaults vs overriding them) and the separate persistent-data directory that survives updates — you'll want the equivalent for generated assets and caches that must outlive a registry rewrite.

**MCP tools: dynamic discovery & listChanged** — Expose the suite's registry as a local MCP server declaring `listChanged: true`; when the founder commits a new pipeline YAML, emit the notification and the running agent session picks it up mid-conversation. Safety rails quoted from the spec: 'clients MUST consider tool annotations to be untrusted unless they come from trusted servers'; there SHOULD always be a human in the loop able to deny invocations; clients SHOULD show tool inputs to the user before calling, 'to avoid malicious or accidental data exfiltration'.

**Programmatic tool calling / code-execution-as-tool-use** — Critical rail, quoted verbatim from the docs: '`allowed_callers` controls how the tool is presented to Claude and is validated against `tool_choice`, but it is not a hard API-level block on direct invocation… Do not rely on `allowed_callers` as a security boundary.' Your client must still handle a direct tool_use for any tool it defines. Docs also advise choosing either `["direct"]` or `["code_execution_…"]` per tool rather than both, for clearer guidance.

**Agent Skills security guidance (Anthropic)** — For a creative suite that personalises decks per prospect, the agent WILL fetch prospect websites and LinkedIn pages. That is precisely the 'external URLs may contain malicious instructions' case. Mitigation: fetched prospect content must enter as clearly-delimited untrusted data in a separate context slot, never as instructions, and no publish/spend verb may be reachable from a turn whose context contains freshly-fetched external text without an explicit human approval.

**Vercel AI SDK — createOpenAICompatible** — Verified that the whole config is data: `const provider = createOpenAICompatible(JSON.parse(process.env.PROVIDER_CONFIG))`. Your provider descriptor's `adapter: openai-compatible` branch is then a ~10-line mapping from YAML to this call.

**Vercel AI SDK — createProviderRegistry** — Two things worth noticing: `videoModel()` exists and the doc's own example is a fal video model, so the media side is first-class rather than bolted on; and the middleware arrays are the natural insertion point for cost accounting, era-tagging and budget enforcement across every provider at once — you implement governance (requirement c) in one place, not per provider.

**LiteLLM proxy config.yaml + custom pricing** — `input_cost_per_video_per_second` and `input_cost_per_second` are precisely what a creative suite needs and what most abstractions forget. Reusing LiteLLM's exact key names means you can seed your provider registry from their community-maintained model_prices JSON and stay diff-able against it. The `os.environ/VAR` indirection convention is also worth copying so secrets never land in the git-of-truth.

**LiteLLM tag-based routing** — Honest limitation, confirmed by the docs themselves: tags are opaque strings, not capability declarations. `["video","9x16"]` carries no semantics the router can reason about — it cannot know 9:16 is an aspect ratio or that 30s exceeds a model's max duration. That is exactly why your provider descriptor needs typed `constraints` (aspect list, max_duration_s, languages) rather than a tag soup.

**OpenRouter provider preferences (capability-constrained routing)** — Map almost 1:1 onto your pipeline's `constraints:` block: `max_price` → `max_cost_try`, `sort` → `prefer: cost|speed|quality`, `require_parameters` → your hard capability filter, `only`/`ignore` → the founder's per-era provider allow/deny list (requirement c). The gap is that `max_price` is token-denominated and text-only; media pricing is per-second/per-image, so your cost formula layer has to exist regardless.

**OpenRouter /api/v1/models metadata** — Fetched live and verified. `expiration_date` and `knowledge_cutoff` are the fields most people miss and the ones that make a registry self-maintaining: a weekly job can flag descriptors whose upstream model is scheduled for retirement, which is how you stop a pipeline silently breaking a year from now.

**fal.ai per-endpoint OpenAPI documents** — This is the highest-leverage discovery in this research. You do not write provider descriptors for fal models; you paste an endpoint id and an importer pulls the OpenAPI, derives the param schema, defaults, ranges and enums, and proposes a descriptor for the founder to annotate with capability tags, quality tier and cost formula. Ranges and enums come across too, so your validator can reject `num_inference_steps: 90` before spending anything. Same technique works for any provider publishing OpenAPI.

**Helicone AI Gateway (helicone-router)** — Performance claims are the project's own and UNVERIFIED. Text/chat oriented — it will not route your image/video steps, so it can at best own the LLM half. For a solo operator the real appeal is that observability, caching and per-key spend limits arrive as config rather than code. Weigh against one more moving part in the stack.

**Zod v4 JSON Schema conversion** — `io: 'input'` matters more than it looks: your pipeline schema has defaults and coercions, and the form the founder fills in is the INPUT shape while the executor sees the OUTPUT shape. Emit the input variant for rjsf and the output variant for the executor's contract. `z.fromJSONSchema()` is the escape route for importing fal's OpenAPI input schemas straight into your validation layer.

**react-jsonschema-form (@rjsf)** — Directly satisfies requirement (a): the founder adds a persona field to a schema file and the form grows a field with no rebuild. Keep `uiSchema` as a sibling file (`*.ui.yaml`) so presentation is also data and the agent can propose ordering/widget choices without touching the data contract. UNVERIFIED: exact JSON Schema drafts supported (docs didn't state; ajv8 implies 2020-12 and draft-7).

**node:vm** — Worth stating explicitly in the design doc because it is the default thing a solo developer reaches for and the docs disclaim it in one sentence. `timeout` still helps against accidental infinite loops in your own template engine, but it is a reliability feature, not a security one.

**isolated-vm** — Author's own warning, quoted: 'Use of isolated-vm to run untrusted code does not automatically make your application safe. Through carelessness or misuse… it can be possible to leak sensitive data.' Never hand References/ExternalCopy objects into an untrusted isolate; keep it in a separate process from anything critical; keep Node patched for V8 CVEs. The native-addon-per-Node-version matrix alone will cost you an afternoon on every Node upgrade.

**quickjs-emscripten** — Honest caveat from the README: pre-1.0 with expected breaking API changes, and 'makes every effort to be secure, but has not been audited.' That is acceptable for evaluating arithmetic cost formulas and template expressions with a 10ms deadline, a few MB cap and zero host bindings — the blast radius is a wrong number, not a compromised machine. Do not use it to run user code that needs network.

**Deno permissions** — Two documented escape hatches you must never grant: `--allow-run` ('runs as a separate program with its own permissions, not the restricted set you granted', and `--allow-run=deno` lets it relaunch with `--allow-all') and `--allow-ffi` ('can issue system calls directly… regardless of which --allow-* flags you passed'). Docs say to 'treat as equivalent to --allow-all'. Also: `--allow-write` on a directory containing allowed executables lets a script overwrite a binary that later gets run. Practical rule — a pipeline's script step declares its egress hosts in the YAML, and the runner translates that to `--allow-net=<exact hosts>` with everything else denied.

**workerd** — Quoted: 'workerd tries to isolate each Worker so that it can only access configured resources. However, workerd on its own does not contain suitable defense-in-depth against implementation bugs' — running potentially malicious code requires wrapping it in a VM, and Cloudflare's hosted service has additional layers not in the OSS build. So it buys you a second config language and an ops burden without buying the security guarantee. UNVERIFIED: licence (README didn't state it; believed Apache-2.0).

**ComfyUI API workflow format** — The format split is the design lesson: ComfyUI's *executable* representation is a flat map of `{id: {class_type, inputs}}` and everything else is renderer state. That is an argument for making your canonical pipeline format the executable one and treating any future visual editor as a projection over it — the opposite of n8n/Langflow, where the canvas format IS the file. If the founder ever wants local, free, brand-consistent image generation with LoRAs, wrap ComfyUI behind a `provider` descriptor with `adapter: comfy` and a workflow template. UNVERIFIED: exact API JSON shape (docs page didn't show it).

**Flowise** — The Apache-2.0 portion has no hosting restriction, so internal use is unproblematic; the risk is architectural rather than legal. Listed mainly so the founder knows it was considered and why the graph-canvas family was rejected as a definition format: agent-authorability is the deciding criterion and edge-list JSON loses on it.

**Dify** — UNVERIFIED: Dify is widely believed to export apps as a versioned YAML DSL, which would have been strong prior art for a data-defined pipeline format. The docs page I fetched covers only the visual builder and says nothing about export formats or a DSL version field. I am deliberately not asserting the DSL structure from memory. If this matters, fetch docs.dify.ai/llms.txt and locate the DSL reference before relying on it.

### Öneriler

- PIPELINE FORMAT — adopt a flat, ordered, typed step list, not a node graph. `apiVersion: creative/v1`, `kind: Pipeline`, `id`, `title`, `era`, `version`, then four blocks: `inputs:` (a JSON Schema object → auto-renders the run form via rjsf and validates via ajv), `context:` (declarative memory selection: `include:` entries of kind dna/entity/memory with era, sections, query, top_k, pinned_first, plus `budget_tokens`), `steps:` (each `{id, uses, needs[], with{}, foreach?, approval?}`), and `outputs:` + `policy:` (`budget_try`, `max_wall_seconds`, `on_error`). Rationale, from the evidence: Kestra proves a flat `{id, type, params}` list scales to hundreds of task types; GitHub Actions' `uses`/`with`/`needs`/`{{ }}` is the densest workflow dialect in LLM training data and therefore the most reliably agent-authorable; ComfyUI's own executable format collapses to a flat map, showing the canvas is incidental.
- CAP THE VERB COUNT AT ~8 AND DEFEND IT. `llm.generate`, `image.generate`, `video.generate`, `tts.generate`, `render.*`, `channel.publish`, `human.approve`, `script.run`. A new creative job type must be expressible as a new arrangement of existing verbs plus data; if it is not, that is the rare signal that a developer is genuinely needed. This cap is the single decision that keeps the system maintainable by one person — every abstraction layer you add past this point makes it a worse n8n.
- STEPS DECLARE CAPABILITIES, NEVER MODEL IDS. `with: {capability: video.text2video, constraints: {aspect: '9:16', max_duration_s: 30, language: tr, max_cost_try: 5}}`. A model id in a pipeline file is a hardcoded brand assumption by another name, and it violates requirement (d) the day a provider dies. Resolution happens at plan time and is recorded in the run manifest, so pipelines survive provider churn while past runs stay explainable.
- PROVIDER DESCRIPTOR — one YAML file per provider with exactly these blocks: `id`, `title`, `adapter` (one of a handful of built-in transports: openai-compatible, fal.queue, replicate, http.json, comfy, local), `endpoint`, `auth` (`${ENV_VAR}` indirection only — never literals in the git-of-truth, copying LiteLLM's `os.environ/VAR` convention), `schema_source` (an OpenAPI URL to import params from), `capabilities[]` (tags mirroring OpenRouter's `input_modalities`/`output_modalities` vocabulary), `constraints{}` (typed: aspect list, max_duration_s, languages, audio bool, max_resolution), `params{}` (canonical→native mapping with optional transforms), `cost{formula, currency, fx}`, `latency_p50_s`, `quality_tier` (1–5, founder-editable), `enabled`. Reuse LiteLLM's exact cost key names (`input_cost_per_token`, `input_cost_per_second`, `input_cost_per_video_per_second`, `input_cost_per_image`) wherever a flat rate suffices, so you can seed from their community price data and stay diff-able against it.
- BUILD THE PROVIDER IMPORTER FIRST — it is the highest-leverage thing in this whole design. fal serves a complete OpenAPI 3.0.4 document per model endpoint at `https://fal.ai/api/openapi/queue/openapi.json?endpoint_id=<id>` (verified live), OpenRouter serves capability + pricing metadata at `/api/v1/models` (verified live), and `z.fromJSONSchema()` ingests either. So 'add a provider' becomes: paste an endpoint id → importer derives params, ranges, enums and defaults → proposes a descriptor → founder annotates capability tags, quality tier and cost formula → commit. Under 60 seconds, and the imported ranges let the validator reject bad params before spending money.
- CAPABILITY ROUTING — implement filter → price → score → fallback, and write down why each loser lost. (1) Hard filter on declared capability tag + typed constraints + `enabled` + the era's allow/deny list. (2) Evaluate `cost.formula` against the concrete params in QuickJS with a 10ms deadline, convert USD→TRY at a cached daily rate, drop anything over `max_cost_try`. (3) Score survivors as a weighted sum of quality_tier, −normalised cost and −latency, with weights from the pipeline's `prefer: quality|cost|speed`. (4) Ordered fallback chain on error or timeout. (5) Persist the winner AND the full candidate list with rejection reasons into the run manifest. Step 5 is what turns routing from magic into governance (requirement c). Constraint vocabulary comes from OpenRouter (`sort`, `max_price`, `only`, `ignore`, `allow_fallbacks`, `require_parameters`); the AND/OR/NOT algebra and `allow_fail_open` degradation come from LiteLLM tag routing.
- BE HONEST THAT THE MEDIA ROUTER IS YOURS TO WRITE. No OSS system today answers '9:16 video with Turkish voiceover under 30s for under 5 TL'. OpenRouter's `max_price` is per-million-tokens and text-only; LiteLLM tags are opaque strings with no semantics; Helicone balances latency and cost but not media capability. The gap is roughly 300 lines over typed descriptors. That is a feature — it is small, it is the actual product differentiator, and it is the one part no dependency can rot out from under you.
- VALIDATION — four gates, in this order, before anything can run. (1) SCHEMA: file matches pipeline.schema.json. (2) GRAPH: every `needs` resolves, the DAG is acyclic, and every `{{ }}` expression resolves to a declared input, a prior step's declared output, or a context key. Gate 2 catches nearly every agent-authored mistake and is the highest-value 100 lines in the codebase. (3) RESOLVE: every step's capability has at least one enabled provider surviving its constraints, or fail with a specific message — 'no provider satisfies video.text2video at 9:16 ≤30s under 5.00 TL; cheapest candidate kling-v2-master estimates 7.40 TL'. (4) PLAN: a Terraform-plan-style dry run printing the DAG, the chosen provider per step, an estimated cost band, the token budget and the exact context that would be injected — calling nothing paid. Windmill's per-module `mock:` is the closest OSS analogue; adopt the idea.
- ONE ZOD SCHEMA, FOUR OUTPUTS. Define pipeline/provider/channel schemas once in Zod v4, then `z.toJSONSchema()` to produce: the ajv validator, the `# yaml-language-server: $schema=` editor autocomplete, the rjsf form in the command center, and the reference file the authoring skill reads. Emit `io: 'input'` for forms and `io: 'output'` for the executor contract — your schemas have defaults and coercions, so the two shapes genuinely differ. Wrap ajv errors: raw ajv output is unreadable, so every failure must name the file, the JSON pointer, what was expected, and one suggested fix.
- VERSIONING — freeze the plan, don't version the file. On trigger, hash (pipeline file + every referenced prompt/schema + the resolved provider descriptors + the context snapshot + the era id) into a `definition_digest`, and write `runs/<id>/manifest.json` containing the git commit SHA, the digest, the fully-resolved plan after all substitution, provider ids and resolved params, model ids, seeds, actual cost and the injected context verbatim. Then expose two distinct actions, copying Trigger.dev's semantics exactly: `rerun` executes the frozen plan (reproducible), `replay` runs the same inputs against today's definition (shows drift). This sidesteps Temporal's entire determinism/patching problem class rather than solving it, and it makes requirement (b) fall out for free — assets carry `era` + `definition_digest`, so a DNA regeneration mints a new era while old assets stay correctly tagged to the old one.
- SANDBOXING — three tiers, and reject the tempting middle. Templates and cost formulas: QuickJS via quickjs-emscripten with `memoryLimitBytes` and `shouldInterruptAfterDeadline`, no host bindings (blast radius = a wrong number). User scripts needing network: a Deno subprocess with an egress allowlist declared in the pipeline YAML and translated to `--allow-net=<exact hosts> --allow-read=./workspace`, never granting `--allow-run` or `--allow-ffi` (Deno's own docs say treat those as `--allow-all`). Never `node:vm` — the docs disclaim it in one sentence: 'not a security mechanism'. Skip isolated-vm (maintenance mode, native-addon rebuild per Node version) and workerd (its README states it lacks defence-in-depth against implementation bugs and needs a VM around it). Single-user single-tenant means the real threat is your own agent erring and injected instructions from a scraped prospect page — you need to bound egress, filesystem and spend, not defeat a determined attacker.
- PLUGIN ARCHITECTURE — copy Claude Code's convention-first model exactly. Manifest optional; components auto-discovered by directory (`registry/pipelines/`, `registry/providers/`, `registry/channels/`, `registry/schemas/`); paths `./`-relative; a manifest exists only to override defaults, with an explicit ADD-vs-REPLACE distinction; and a separate persistent-data directory for generated assets and caches that must outlive a registry rewrite. Do NOT build a general plugin API with lifecycle hooks — for a solo maintainer, a data registry plus ~8 fixed verbs is strictly better than an extension framework nobody else will ever write against.
- HOT RELOAD — reload data, restart code. chokidar-watch `registry/**` → re-parse → re-validate → push results to the Next.js command center over SSE. Registry reload is safe because it is data; dynamic re-import of TS modules is not, so a new verb means a restart, which is fine at ~twice a year. If the command center also exposes an MCP server to the agent, declare `tools.listChanged: true` and emit `notifications/tools/list_changed` when the registry changes — a running agent session then discovers a newly-added pipeline mid-conversation with no restart.
- AGENT AUTHORING — ship a `new-pipeline` skill and a `pipeline-author` subagent, with the rails switched on. Write the skill to the agentskills.io spec (name ≤64 lowercase-hyphen matching its directory, description ≤1024, body <5k tokens and <500 lines, schema details in `references/`) so it stays portable if the founder ever leaves Claude Code. Set `disable-model-invocation: true` on every side-effecting skill (publish, deploy, spend) so Claude cannot fire them unprompted. Grant `allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/validate.sh *)` — the variable is substituted in both the body and the Bash rule, so the validator runs prompt-free and nothing else does. Give the subagent `isolation: worktree` so registry rewrites land in a throwaway worktree and the founder reviews a real diff.
- THE ONE INVIOLABLE RAIL: the agent may WRITE registry YAML; only the founder may APPLY it. Apply is a git commit (or a signed approval in the command center that makes one). Diff-review-then-commit is the entire safety story for self-modifying config, it costs nothing because the repo is already the source of truth, and it is the only mechanism here that degrades gracefully when the model is wrong.
- TREAT FETCHED PROSPECT CONTENT AS HOSTILE INPUT. Personalising decks means the agent will read prospect websites and profiles — precisely the case Anthropic's skills docs flag as highest-risk ('fetched content may contain malicious instructions'). Inject external text into a clearly-delimited untrusted context slot, never as instructions, and make it structurally impossible for a publish or spend verb to fire in a turn whose context contains freshly-fetched external text without an explicit human approval. Note also that Anthropic's docs explicitly say `allowed_callers` is 'not a hard API-level block' and must not be relied on as a security boundary.
- ADDING A NEW CREATIVE JOB TYPE, THE 10-MINUTE PATH: (1) `/new-pipeline instagram reels teaser, 9:16, Turkish VO, under 20s` — the skill loads and reads the schema reference plus existing pipelines [~30s]. (2) Claude writes `registry/pipelines/reels-teaser.pipeline.yaml` [~1min]. (3) `creative validate reels-teaser` — schema, DAG, reference and provider-resolution gates; any failure names file + pointer + fix [~5s]. (4) `creative plan reels-teaser --topic dima --persona factory-cfo` — prints the DAG, the chosen provider per step, a 4.20 TL estimate and the exact context to be injected; spends nothing [~10s]. (5) founder reads the diff and approves → commit [~2min of real reading]. (6) run. Under 5 minutes of human time, leaving headroom for one round of 'no, cheaper, different voice model'. Adding a provider is faster (paste endpoint id, importer proposes, annotate, commit); adding a channel is a `registry/channels/x.channel.yaml` with `publish.adapter`, `auth`, `constraints` (max chars, media types, aspect ratios) and `preview.template`, consumed by the existing `channel.publish` verb.


### Riskler

- METHODOLOGY RISK, STATED UP FRONT: this session's WebSearch budget (200/200) was exhausted before my first query, so I could run zero searches. Everything above comes from direct WebFetch of primary docs and repos I could name from prior knowledge. This biases coverage toward tools I already knew existed — a genuinely new 2026 entrant in declarative agent-pipeline formats would not have surfaced. Re-run the search-based sweep before treating this as exhaustive.
- OVER-GENERALISATION IS THE PRIMARY FAILURE MODE. The founder's requirement (everything must be data) pulls toward making every verb configurable, at which point the suite becomes a worse n8n that only one person maintains. The verb cap is the load-bearing constraint; if the count drifts past ~10 the project has failed even if every individual decision looked reasonable.
- COST FORMULAS AS DATA MEANS ARBITRARY EXPRESSION EVALUATION IN A BUDGET-CRITICAL PATH. A wrong formula silently under-estimates and the budget gate waves through a run that costs 10x. Mitigate with a QuickJS 10ms deadline and no globals, plus a post-run reconciliation that diffs estimated against actual cost per provider and flags drift over 20%.
- PROVIDER CAPABILITY DRIFT IS SILENT. Descriptors written today go stale as endpoints change params, raise prices or retire. OpenRouter publishes `expiration_date` and `knowledge_cutoff` and fal republishes OpenAPI, so a weekly `creative doctor` that re-pulls upstream metadata and diffs against local descriptors is cheap insurance. Without it, a pipeline breaks a year from now with an unhelpful 422.
- YAML FOOTGUNS. YAML 1.1 parses `no` as boolean false and `tr` stays a string but `on`/`off`/`yes` do not — an aspect ratio or a language code can silently change type. Pin the `yaml` package to YAML 1.2 core schema, and quote every enum-ish scalar in generated files.
- TURKISH LOCALE STRING HANDLING. A Node process running under tr_TR will map 'I'→'ı' and 'i'→'İ' in `toLowerCase()`, which corrupts ids and slugs in ways that are maddening to debug. Force `toLowerCase('en-US')` (or better, validate ids against `^[a-z0-9-]+$` and never transform) everywhere in the registry loader.
- LICENCE LANDMINES IF THE SUITE IS EVER PRODUCTISED. n8n's Sustainable Use License permits internal business use but is not OSI open source and restricts providing the software to third parties — fine internally, a problem if Upcytech ever sells or hosts the creative suite. Windmill's repo mixes AGPLv3 with proprietary enterprise code and its Community Edition binary is restricted from resale. Flowise carves out `/packages/server/src/enterprise` under a commercial licence. Given the stated repositioning toward SaaS, prefer Apache-2.0/MIT dependencies (AI SDK, LiteLLM, Helicone gateway, rjsf, Zod, quickjs-emscripten, Trigger.dev) and avoid embedding the copyleft/source-available orchestrators entirely.
- isolated-vm IS IN MAINTENANCE MODE with an experimental rewrite the author calls not production-ready, and it needs a native rebuild per Node major (Node 26 → v7, `--no-node-snapshot` required on ≥20). Choosing it commits a solo maintainer to an afternoon of pain on every Node upgrade, for a security property the author explicitly says is not automatic.
- quickjs-emscripten IS PRE-1.0 AND UNAUDITED by its own README, with expected breaking API changes. Acceptable for arithmetic expressions with a deadline and no host bindings; not acceptable if scope creeps toward running user-authored logic with data access.
- GRAPH VALIDATION IS THE THING MOST LIKELY TO BE SKIPPED AND MOST EXPENSIVE TO OMIT. Schema validation catches shape errors, but agent-authored pipelines fail overwhelmingly on unresolvable `{{ steps.foo.output.bar }}` references and on `needs` pointing at renamed steps. If gate 2 is deferred to 'later', the founder's experience of agent-authored pipelines will be runtime failures halfway through a paid run.
- FROZEN PLANS GROW UNBOUNDED. Storing the fully-resolved plan plus the verbatim injected context per run is what makes reruns reproducible and governance real, but at a few hundred KB per run it needs a retention policy from day one — keep manifests forever, keep context snapshots for N days, and content-address large blobs so identical contexts store once.
- MEDIA PROVIDER NON-DETERMINISM CAPS REPRODUCIBILITY. Even a bit-identical frozen plan will not reproduce a video, and many endpoints ignore or do not expose seeds. Be explicit in the UI that `rerun` reproduces the DECISION (same provider, same params, same context), not the ARTEFACT — otherwise the founder will read a mismatch as a bug in the suite.
- SINGLE-OPERATOR BUS FACTOR ON THE ROUTER. The capability router is the one component with no upstream to fall back on. Keep it under ~300 lines, table-driven, and covered by fixture tests that assert 'given these descriptors and this constraint set, this provider wins and these lost for these reasons' — so it stays legible a year later.
- MCP `listChanged` DEPENDS ON CLIENT COOPERATION. The spec says servers SHOULD notify and clients then re-list, but a client that ignores it leaves a stale tool set until restart. Do not make mid-session registry discovery load-bearing for the 10-minute workflow; treat it as a convenience with a restart as the guaranteed path.
