## Özet

Verified against primary docs/repos on 2026-08-14. The market has split into three layers, and only one of them belongs in Upcytech's system of record.

Layer 1 — memory *services* (Mem0 63.2k★ Apache-2.0, Cognee 30k★ Apache-2.0, Supermemory 28.9k★ MIT, Memobase 2.8k★ Apache-2.0, Letta 24.2k★ Apache-2.0, Redis Agent Memory Server Apache-2.0). All self-hostable, all expose CRUD, several now ship contradiction resolution and temporal forgetting. But every one of them makes an LLM the author of memory and the human the reviewer-after-the-fact. That inverts requirement (c). Two once-recommended options are now dead: Zep Community Edition is explicitly "no longer supported… moved to legacy/", and Motorhead states "Support is no longer maintained." Do not build on either.

Layer 2 — the temporal model. Graphiti (29.9k★, Apache-2.0) is the correct reference. Its `EntityEdge` carries four verified timestamps — `created_at`, `expired_at` ("datetime of when the node was invalidated"), `valid_at` ("when the fact became true"), `invalid_at` ("when the fact stopped being true") — plus `episodes` (provenance), `attributes`, and developer-defined entity/edge types via Pydantic. "Facts have validity windows. When information changes, old facts are invalidated — not deleted." That is exactly requirement (b). Copy the *schema*, not necessarily the Neo4j/FalkorDB dependency.

Layer 3 — Anthropic-native, and the strongest 2026 signal. Claude Code now has two documented systems: author-written `CLAUDE.md` + `.claude/rules/*.md` with `paths:` glob frontmatter (conditional loading), and *auto memory* — `~/.claude/projects/<project>/memory/MEMORY.md`, first 200 lines/25KB loaded per session, `modified` ISO-8601 frontmatter stamped on write, browsable/editable via `/memory`, verifiable via `/context`. The API memory tool is GA (`memory_20250818`, no beta header, all Claude 4+ models) and is explicitly **client-side**: "Memory lives entirely in your application." Letta's 2026 pivot (letta-code, Apache-2.0) landed on the same answer: **MemFS, a "git-backed memory filesystem that they can inspect and edit."**

Conclusion: build a git-backed, file-per-fact memory with Graphiti's bi-temporal fields, a SQLite/FTS5 disposable index, and a proposal-inbox write path. Adopt no memory SaaS as source of truth.

### Öneriler

- STORAGE — git repo of truth, one file per fact. Store every memory as a Markdown file with YAML frontmatter under memory/<entity_type>/<slug>.md. Frontmatter fields (copied from Graphiti's verified EntityEdge plus provenance): id, type, claim, body, source{kind: interview|url|file|inference, ref, quote}, confidence(0-1), approved_by, approved_at, created_at, valid_at, invalid_at, expired_at, era_id, supersedes[], superseded_by, status(draft|active|pinned|retired), scope{channels[], verticals[], personas[]}, tags[]. Git gives you free versioning, diff, blame, revert, branch and PR review — the entire 'see everything, edit it, retire it' requirement is satisfied by tooling that already exists and that one person can maintain forever. This is not a novel bet: Letta's 2026 MemFS is literally 'a git-backed memory filesystem that they can inspect and edit', and Anthropic's GA memory tool is client-side by design ('Memory lives entirely in your application'). Do NOT put brand DNA inside Mem0, Cognee, Supermemory, Letta Cloud or Zep Cloud. Those are indexes; git is the record.
- INDEX — SQLite as a disposable derivative. Build memory.db from the repo with a pure function: a `cards` table mirroring the frontmatter (era_id, status, valid_at, invalid_at, expired_at, confidence, scope columns) + an FTS5 external-content table (content='cards', content_rowid='rowid') kept in sync by triggers. Query with bm25() and per-column weights so `claim` outranks `body`. `npm run reindex` must be able to nuke and rebuild the whole thing from git in seconds. Because the index is derivable, an FTS5 schema change or a sqlite-vec breaking upgrade is an inconvenience, never data loss. Turkish note: FTS5's unicode61 tokenizer strips diacritics by default (good for ı/İ/ş/ğ/ç/ö/ü) but there is no Turkish stemmer — pair unicode61 with a trigram index for substring robustness on Turkish morphology.
- SEARCH THRESHOLD — a concrete answer. Under ~1,500 memory cards / ~2M tokens of corpus (which is where a solo founder's brand DNA, product facts, prospect notes and asset history will sit for years): FTS5 BM25 + a disciplined file layout + era/scope filters is not merely sufficient, it is BETTER, because results are explainable ('matched term X, score Y') and explainability is the actual requirement here. Add sqlite-vec embeddings ONLY when one of three things becomes true: (1) card count passes ~2,000-5,000 and BM25 recall visibly misses paraphrases; (2) you routinely search in Turkish for concepts written down in English or vice versa — cross-lingual recall is the single strongest reason to add embeddings for this specific company; (3) queries become intent-shaped ('facts that argue Upcytech is R&D-heavy') rather than term-shaped. When you add them, add them as a RERANKER over the FTS5 top-50, not as the primary retriever — you keep the explainable first stage. Do not run Meilisearch or Typesense; a second daemon buys nothing at this scale and Typesense is GPL-3.0.
- ERA MODEL — versioned, re-runnable brand discovery. Define an `eras/` directory: each era is a manifest {era_id, name, started_at, ended_at, discovery_run_id, rationale, status}. Every card carries era_id. Every generated asset (post, deck, video, ad) records era_id + the ordered list of card ids and content hashes that produced it. Retirement is NEVER deletion: set expired_at + superseded_by and flip status to retired, exactly as Graphiti does ('old facts are invalidated — not deleted'). Retrieval defaults to `WHERE era_id = :current AND expired_at IS NULL AND (invalid_at IS NULL OR invalid_at > now())`, so a retired 2024 recycling-sector positioning can never leak into a 2026 manufacturing deck — while a 2024 asset still resolves correctly against its own era for audit. Point-in-time view is one query parameter away.
- DISCOVERY AS A JOB, NOT A FORM. 'Run brand discovery again' creates a git branch, not an overwrite. The discovery agent writes proposed cards into that branch with status: draft. The command center renders a three-column reconciliation view — UNCHANGED / CHANGED / CONTRADICTED / NEW — where every contradiction shows old claim, new claim, both sources, both confidences, and three buttons: keep old, accept new (auto-writes supersedes/superseded_by), or keep both scoped differently. Merging the branch mints era N+1. This makes 'regenerate everything from scratch' and 'I don't like this, run it again' into ordinary, reversible git operations rather than a data migration.
- SCHEMAS AS DATA — requirement (a) solved without a developer. Keep JSON Schema documents in schemas/*.schema.json (product_type, vertical, channel, persona, prospect, asset_kind). Validate with Ajv; render create/edit forms directly from the schema in Next.js. Adding a new product type, vertical, channel or persona field = editing or adding a schema file through a UI schema editor, committed to git, with a migration preview showing which existing cards now fail validation. Graphiti proves the pattern works ('developer-defined entity and edge types via Pydantic models', supporting 'both prescribed and learned ontologies') — you are simply moving the definition from code to a data file so the founder, not a developer, owns it. Schemas are themselves versioned and era-tagged, so requirement (d) — the company transforming entirely — is a new schema set plus a new era, not a rewrite.
- CONTEXT GOVERNANCE — declarative recipes with per-section token budgets. Define context recipes in YAML per task type (instagram_post, linkedin_post, sales_deck, demo_video, ad_creative). Each recipe is an ordered list of sections, each with a source (always_on | pinned | retrieved | entity | prospect | asset_history), a selector, and a hard token budget: e.g. brand_invariants: always_on, 1200 tokens; positioning: pinned, 800; supporting_facts: retrieved(bm25, k=12), 3500; prospect_dossier: entity(prospect), 2000; recent_assets: retrieved(recency), 1000. The assembler fills each section to budget in score order, drops the overflow, and emits a MANIFEST: every card id, its section, why it was chosen (always-on / pinned by human / BM25 score 8.4), and its exact token count. Borrow Cursor's four-mode taxonomy for the per-card entry policy: Always / Agent-decides-by-description / Scoped-by-glob-or-facet / Manual-pin.
- PREFLIGHT PREVIEW — the screen that makes the founder trust the system. Before any generation, show the assembled context: a stacked bar of sections against the model's window (this is /context, but a real UI), the full rendered prompt text, and a card list where each row shows claim, source, confidence, era, why-included, token cost, and a toggle. Toggling a card off recomputes the bar live and is recorded as a run-scoped override. Get the token numbers EXACTLY right by calling the Anthropic count_tokens endpoint, which accepts context_management so the preview reflects post-editing reality rather than a guess. Add a 'diff vs last run' view so the founder can see what changed in what the agent knows since the last time this deck was generated.
- WRITE PATH — a proposal inbox, never direct agent writes. This is the hard line that separates your system from every product in the survey. Agents may only call memory.propose(); proposals land as status: draft with source.kind = inference and the originating run_id. Nothing enters retrieval until a human approves it, which stamps approved_by/approved_at and flips status to active. Letta's 'dreaming' (background subagents consolidating memory), Mem0's automatic extraction and Redis's background promotion all write autonomously — steal their extraction quality, reject their write authority. Practical consequence: an approvals queue with a keyboard-driven approve/reject/edit flow is a first-class screen, not a settings page.
- CONFLICT DETECTION AND ARBITRATION. On every proposed write, run a two-stage check against active cards in the same (type, scope) slot: FTS5 near-duplicate retrieval, then a cheap LLM contradiction classifier (entails / contradicts / unrelated) over the top candidates. A 'contradicts' verdict never auto-resolves — it opens an arbitration item showing both claims side by side with their sources, dates and confidences. Mem0's `replaced_by` field and Graphiti's edge invalidation are the two verified precedents for the supersedes-link; the arbitration UI is what neither of them gives you.
- AUDIT — bidirectional traceability. Persist a run record for every generation: {run_id, task_type, recipe_version, era_id, model, provider, input/output tokens, cost, context_manifest[{card_id, content_hash, section, reason, tokens}], prompt_hash, output_path, output_hash, overrides[]}. Push the same manifest to a self-hosted Langfuse (MIT core, 33.1k★, team joined ClickHouse — the healthiest maintenance signal in this survey) as trace metadata. Then build the reverse index: from any card, list every asset it ever influenced. A bad post traces to a bad fact in two clicks; fixing that fact immediately shows every other asset now suspect. Also log Claude's context_management.applied_edits into the run record so you can prove nothing was silently cleared mid-run.
- MODEL, PROVIDER AND BUDGET GOVERNANCE. Keep a models.yaml in the repo mapping task class → provider, model id, max output tokens, thinking budget, monthly spend cap, and fallback. It is git-versioned like everything else, so 'which model wrote this' is answerable retroactively. Surface spend by task type, era and month in the command center. Because the run record already stores model + tokens + cost, this dashboard is a SQL query, not a subsystem.
- ANTHROPIC-NATIVE INTEGRATION — the recommended 2026 pattern. Use each mechanism for what it is actually good at, per the verified docs: (1) CLAUDE.md + .claude/rules/*.md with `paths:` frontmatter for durable OPERATING INSTRUCTIONS, scoped so they only load when relevant; (2) Agent Skills for PROCEDURES (how to build a deck, how to storyboard a demo video) — progressive disclosure means Level-3 reference files cost zero tokens until read, so a skill can bundle the entire brand book; (3) your governed repo, exposed as an MCP server with tools memory.search / memory.get / memory.propose, for FACTS; (4) the GA memory tool (memory_20250818) pointed at a scratch subdirectory of the same repo if you want the agent's own working notes to be git-visible. Two configuration details that matter: set Claude Code's `autoMemoryDirectory` into the repo so auto memory stops being invisible machine-local state, and pass `exclude_tools: ['memory']` to clear_tool_uses_20250919 so context editing can never delete your retrieved facts mid-run. Use the InstructionsLoaded hook to log exactly which instruction files loaded per session — free audit trail.
- UI SURFACE — seven screens. (1) MEMORY BROWSER: faceted table over all cards — filters for era, type, status, scope, confidence, source kind, age; inline edit that writes the Markdown file and commits; bulk pin/retire; a status chip per row (draft/active/pinned/retired) and a staleness chip driven by the `modified`-style timestamp. (2) CARD DETAIL: claim, body, provenance with the source quote, confidence slider, approval trail, git history of this file, supersedes/superseded-by chain rendered as a timeline, and 'assets influenced by this card'. (3) ERA TIMELINE: horizontal band of eras with card counts and asset counts; clicking an era switches the whole app into that era's point-in-time view (read-only for past eras). (4) DISCOVERY / RECONCILIATION: the unchanged/changed/contradicted/new three-column merge view described above, with per-row arbitration. (5) APPROVALS INBOX: keyboard-driven queue of agent proposals with approve / edit-and-approve / reject-with-reason. (6) CONTEXT PREVIEW: the preflight screen — stacked token bar per section, full prompt text, per-card include toggles, diff-vs-last-run. (7) RUN AUDIT: every generation with its manifest, cost, model, era, output, and the reverse index from card → assets. Screens 1, 6 and 7 are the ones that actually deliver requirement (c); build them first and the rest can be scrappy.
- BUILD ORDER for one person. Week 1: repo layout + frontmatter schema + reindex script + FTS5. Week 2: memory browser and card detail (screens 1-2) — nothing else matters until the founder can see and edit everything. Week 3: context recipes + assembler + preview (screen 6). Week 4: run records + audit + reverse index (screen 7), Langfuse optional. Week 5: eras + retirement semantics (screen 3). Week 6: discovery job + reconciliation + approvals (screens 4-5). Only after all of that, and only if recall genuinely disappoints, add sqlite-vec. Resist adopting any of the surveyed memory platforms as infrastructure; harvest their ideas (Graphiti's four timestamps, Mem0's replaced_by, Supermemory's temporal forgetting, Memobase's topic/sub-topic slots for prospect dossiers, Cursor's four rule modes) into a system whose entire state is a git repo you can read with `cat`.


### Riskler

- The dominant OSS memory products invert the governance requirement. Letta 'dreaming', Mem0 automatic extraction, Cognee's improve verb, Supermemory's automatic fact extraction and Redis's background promotion all give the LLM write authority and the human a review-after-the-fact role. Adopting any as the system of record silently violates requirement (c). Mitigation: agents write to a draft/proposal status only, never to active memory.
- Two widely-recommended options are dead. Zep Community Edition: 'no longer supported. Its code has been moved to the legacy/ folder.' Motorhead: 'Support is no longer maintained for this project.' Most 2024-2025 blog guidance still recommends both. Any plan or LLM answer that names them is working from stale training data.
- Redis Agent Memory Server shows the same soft-deprecation shape Zep did — the README now frames the OSS V0 as 'the research foundation' while the managed Redis Cloud service is 'the current supported' path. Assume the OSS branch will drift.
- sqlite-vec explicitly warns 'pre-v1, so expect breaking changes'. Do not let embeddings become load-bearing state. Keep the embedding pipeline reproducible from the git repo so an upgrade means rebuild, never restore-from-backup.
- Graphiti's runtime requires Neo4j 5.26, FalkorDB 1.1.2 or Amazon Neptune (Kuzu is deprecated with removal planned). That is a database daemon a solo founder must patch, back up and upgrade for years. The schema is free; the runtime is not. Adopt the four timestamp fields, defer the graph database until a query genuinely needs multi-hop traversal.
- Every LLM-extraction memory system (Graphiti, Cognee, Mem0, Letta) charges an LLM call per ingested episode and is non-deterministic. A 'regenerate everything from scratch' run over a large corpus therefore has real cost AND will not reproduce the previous run's output. Budget for it and make the reconciliation diff, not the regeneration, the human-facing artifact.
- Claude Code auto memory is machine-local by default (~/.claude/projects/<project>/memory/), excluded from the retention sweep, and shared across worktrees of the same repo. Left at defaults it becomes ungoverned agent knowledge sitting outside the repo of truth. Set autoMemoryDirectory into the repo — or disable it with CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 and rely solely on the governed store.
- MEMORY.md loads only its first 200 lines or 25KB, whichever comes first, and content beyond that is silently dropped at session start. Any governance scheme that assumes 'it's in the file so the agent read it' is wrong. The same class of failure applies to context editing (default: clears at 100k input tokens, keeps 3 tool uses) and to compaction.
- Nested CLAUDE.md files and paths:-scoped rules are NOT re-injected after /compact — they reload only when Claude next reads a matching file. A pinned brand invariant delivered through a scoped rule can vanish mid-session. Deliver true invariants through the always-on section of your own assembler, not through scoped rules.
- Anthropic's docs are explicit that memory files and rules are 'context, not enforced configuration' and that there is 'no guarantee of strict compliance'. Brand-safety constraints (never claim we are a recycling-software company; never overstate certification) must be enforced by a post-generation validator or a PreToolUse-style hook, not by writing them into memory and hoping.
- The API memory tool executes whatever file operation Claude requests, against storage you own. The docs single out /memories/../../secrets.env as the attack. If the memory root is inside the git repo alongside credentials, a path-traversal bug becomes a credential leak. Canonicalise and re-check every path; keep secrets out of the repo entirely.
- Skills and MCP servers are executable trust boundaries — the docs warn that a malicious skill 'can direct Claude to invoke tools or execute code in ways that don't match the Skill's stated purpose', and that skills fetching external URLs are especially risky because fetched content may carry instructions. Prospect research that pulls a company website into memory is exactly this pattern: treat scraped prospect content as untrusted data, never as instructions.
- Era regeneration orphans lineage unless era_id and the card content hashes are stamped onto every asset AT GENERATION TIME. Retrofitting era tags after a regeneration is impossible — the mapping is gone. This is the single highest-cost mistake available in this design and it is cheap to prevent on day one.
- Licence traps: Typesense is GPL-3.0; Meilisearch splits MIT community edition from a commercial/BSL-1.1 enterprise edition; Langfuse keeps enterprise features in a separate ee/ folder under different terms. All fine for an internal self-hosted tool, all worth knowing before anything derived from this ever ships to a client.
- Custom Skills do not sync across claude.ai, the API and Claude Code — each surface is a separate upload with a separate sharing model. Any workflow that assumes one canonical skill set across surfaces will drift. Keep skills in the repo and script the deployment to each surface.
- Two search indexes (e.g. SQLite FTS5 server-side plus Orama client-side) means two things to keep in sync and two places for stale results to appear. Pick one. At this corpus size, one is enough.
- Adopting a memory SaaS 'just for now' is the failure mode that kills requirement (d). The moment brand DNA lives in a hosted store, 'the company may transform entirely one day' becomes an export-and-migrate project instead of a git branch.

- Memobase: whether profile slots are editable through a UI, and whether the topic/sub-topic taxonomy is user-definable at runtime (which would matter for requirement (a)).

- Whether pointing Claude Code's autoMemoryDirectory at a git-tracked repo path is a supported/tested configuration — the setting is documented as accepting any absolute or ~/ path from any settings scope, but repo-committing auto memory is not described as a pattern anywhere I could reach.
